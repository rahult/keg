# Changelog

## [0.15.1] — 2026-11-28

### Added
- **Whether a mailed sender is genuine** (experimental `mail-verdict`, needs `mail`). Mail-in checks SPF, DKIM and DMARC as a message arrives and writes the verdict with it: each check's result and domain, and `from_verified`, true only when DMARC passes and the message names one From address. `keg.mail_from_verified(event)` and `keg.mail_verified_sender(event)` answer an app's agent, only of mail the asker may read. Lookups are bounded (2 s each, 10 s in all, 64 a message, cached for their time, counted with mail's limits); one that runs out says `temperror` and the message is still taken.
- **A member may hold more than one role** (experimental `member-roles`). Each keeps one role as before; an administrator grants and takes more (`keg.grant_role`, `keg.take_role`); every check of a role reads the whole set: asks and their answers, approvals, organisations' tools, audiences, replays, and `keg.actor_has_role(R)` for policies. `keg app members`, the console's Members… and the Mac app's Members sheet show them; `@keg/app` and the Go client grant and read them.
- **The console shows an app's agents' threads.** An app's page (Apps → an app → an environment) has a Threads tab: each thread's agent, organisation, state, what it waits for and until when, and spend; a thread's events, labelled by who wrote each; its asks, with their arguments only as Keg writes them out; and Wake, Stop and a dry Replay where a person may.
- **A node's disk sync mode is its own.** `keg vm disk --sync full|fsync|none` (stopped VM only); `full` stays the default for every node; a lighter mode is said among the node's warnings. On a clean stop or sleep the whole disk is written to permanent storage on every mode.
- **`docker run --init` and `keg run --init`** give PID 1 to Keg's own small init, as Docker's does: it reaps orphans, passes signals on and ends with the command's status. It runs from a sealed copy in memory and holds nothing of the node's memory.
- **Webhooks on a node with no public name**, such as a Mac: deliveries are taken on the node's local names port, which a Mac forwards to its own localhost, with the same checks and limits; `keg app hooks` says where to point a tunnel.
- **`keg app check [NAME]`** (experimental `app-check`) runs a project's check as a piece of work's gate does, with its own database and a fake model, on a read-only copy of the folder, outside a piece of work.
- **Agents:** `thread.waitFor` and `thread.listen` take `match`, so a thread waits for the event about its own ticket and nothing else wakes it; a thread's own tools read the event that started or woke it (`keg.actor_thread_event`); a thread an emitted event starts outlives the emitter, held to its lineage (one budget, at most 100 threads, stopped with its root); `keg.actor_thread_agent()`; a wait is written on the thread as a `wait` event, and a wake says who woke it; an agent may ask no model with `max_usd 0`.

### Fixed
- **Disks.** A disk path given before a node's first start is used, never replaced by a new file on the internal disk; a start refuses a link to nothing and says why. The Mac's free space is checked (a warning under 10 GB, no start under 2 GB) and shown while the node runs. A node whose disk went read-only or failing says so first among its warnings and takes no new work, rather than answering every write with a raw I/O error.
- **Security, from an outside review before release:** a lineage stops whatever its root's state, and only as far as the stopper may read; a job's events count against the lineage of the thread that enqueued it; a feature turned off reaches every app database (numbered tellings, each with a time limit, retried and named to the person if one cannot be told); every invisible character is written out, one to one, and a secret cut by an ask's 200 characters is hidden; at a node with no public name, one sender or a web page cannot stop hook deliveries; `KEG_TEST_MAIL_DNS` is honoured only by a build for tests; `keg app check` reads only inside its project and its machines are the node's.
- **What an ask shows** is written out one to one (a backslash too), so two different arguments are never shown alike; secrets are hidden before anything is written out; `keg app threads … --json` escapes bidi and hidden characters.
- The firewall keeper lets a node go only when its folder has been gone at three checks; a run's walls are checked before its image is fetched; mail-in reaches a Mac node from the Mac itself; every certificate the node signs carries what strict clients (Python 3.13) require; Keg services no longer offer the model gateway as a service to install, and `keg system install models` says why; `keg vm` acts on the node its socket names; `keg settings experimental on|off NAME` says that feature; the SSH door's server advice is not shown on a Mac node; `keg mail` and `keg app hooks` have help for every flag; `make app` mends a Swift dependency left half made.

## [0.15.0] — 2026-11-27

### Added
- **Experimental features.** What a node is still trying is off until a person turns it on: `keg settings experimental` lists each, `on NAME` and `off NAME` turn one on and off (a person's to do; off keeps what it made), and the console (Keg services) and the Mac app (Settings) have them too. Off means off everywhere: the node refuses its requests, the assistant and a chat app are offered none of its tools, its doors and loops stop, and `keg --help`, the console and the Mac app leave out its commands and pages. Experimental in this release: workspaces and the connector door (0.14.0), previews, git in a workspace, the SSH door, `keg setup server`, model providers and SDK-shaped endpoints, the vault's uses by hand, mail in, webhooks and an organisation's tools. A node upgraded with workspaces or a named door keeps those on and says so. [EXPERIMENTAL.md](docs/EXPERIMENTAL.md)
- **The vault, for what you run by hand.** `keg run --name N --secret NAME[,env=VAR|,file=FILE]` gives a container an entry, as a file in `/run/secrets` (in memory, 0400, its user's, read only) or as a variable; running it is the grant of that entry to that container, kept while it is there. In `keg compose up`, a top-level secret marked `external: true` names an entry, given as a file to the services that list it once a person grants it to the project for its folder (`keg vault grant NAME --compose PROJECT [--service S]`). `keg login HOST` keeps a registry's login as `registry/HOST`, used for the pulls and pushes a person asks for there and for the pull of a person's release; an agent's or a work's release pulls with it only by `keg vault grant registry/HOST --registry HOST`, made since it was last set, and a host's login is never sent to another. `keg vault show`, `export` (sealed under a passphrase, never the node's key) and `import` are a person's alone, at a terminal on the node itself, and so is handing an entry by hand (`keg build --secret`, `keg run --secret`, a Compose project's entries): never the console's nor a request's from another machine; each entry a build is handed is written down as `vault.used`. A build is handed an entry at a `RUN --mount=type=secret` step: `keg build --secret id=ID[,entry=NAME]`, a `keg.yaml`'s `build.secrets` granted with `keg vault grant NAME --build SERVICE` (a work's build only by a grant made since the entry was last set), or a Compose service's `build.secrets`, or `docker build --secret id=NAME,src=/dev/null` through Keg's Docker API for a secret the client offers empty (one offered with a value is the client's own, even where an entry has its name); never in a layer, the cache, the image's config, the build's log or its record. `keg vault stale` lists what holds a value from before its entry was last set, `keg vault restart NAME` restarts the containers that do, and a grant a release or build waits for is a Needs-you item with the command that makes it. The Mac app has a Vault page: names, notes, when each was set, grants and what holds an old value, with Set, Grant and Restart, never a value. The assistant can read the vault's names and grants (`keg.vault.list`) and what holds an old value (`keg.vault.stale`), never a value. [VAULT.md](docs/VAULT.md)
- **Hooks: another service tells an app what happened, and that can start a thread of one of its agents.** An app that uses agents declares a hook in a migration, `keg.hook(name, scheme, secret, agent)`, signed as GitHub, Stripe or Slack sign, as a plain HMAC of the body (optionally of a signed time, held near), or `none`. An administrator of an organization asks for that organization's address with `keg.hook_url(name)`, shown once: `https://<the node's public name>/.keg/hooks/<token>`. The node checks the signature with the vault entry granted to the app's service under the hook's secret name, and the app's database writes a delivery once, as an event `keg.hook.<name>` of that organization marked as from outside, which starts the hook's agent. A delivery sent again is known by what its signature covers, never by a header. Every address that is no hook's is answered alike; the node knows every address and its secret in memory, so a request reads no database and no vault; what leads nowhere and what is forged each pay a budget of their own, so a flood of either takes nothing of a verified sender. `keg app hooks APP` lists an app's hooks and what was sent to them, and says of a `none` hook that anyone who knows its address can forge and replay what it takes. See [the agents guide](skills/keg/references/agents.md#hooks-another-service-starts-a-thread) and [PROTOCOL.md](docs/PROTOCOL.md#hooks-keghookstoken).
- **The Go client runs an app's agents.** `k.Agent(name, handler)` and `k.Work` take each thread's wake as `@keg/app` does; a step reads its events, asks the model through the app's door with its claim, runs tools in one transaction with their result (a tool that changes things only on a person's approval of that very call), asks, waits, sleeps, starts a child and ends; a dry replay changes nothing. `ModelBaseURL()` is the address to give an SDK of OpenAI's or Anthropic's.
- **Mail in: a message to an app's address starts a thread of one of its agents.** An app that uses agents declares an address in a migration, `keg.mail_address(word, agent)`; an administrator asks for their organization's with `keg.mail_url(word)`, shown once: `word+<token>@<domain>`. Nothing is taken until a person gives the node a domain (`keg mail domain DOMAIN`, whose MX is theirs to point) and turns it on (`keg mail on`, port 25 unless `--port`; in a Mac's machine only with `--on-a-mac`). The node then takes mail for those addresses only: it never relays, sends or bounces, and refuses what it will not take while the sender is connected, in the same words for every address that is no one's. Every input is bounded (line, commands, recipients, 10 MiB, attachments, time, conversations and messages per network, per address, per app). A message is read by `mail-parser`, never by MIME reading of Keg's own, and written once as an event `keg.mail.<word>` of that organization: its headers, its text and its attachments listed (the small ones kept), escaped, marked as from outside, and its sender `unverified`: no SPF or DKIM is checked. STARTTLS is offered with the node's certificate for the domain where it has one. `keg mail show` says how it stands and what it refused; `keg app mail APP` lists an app's addresses and what was mailed to them. See [the agents guide](skills/keg/references/agents.md#mail-a-message-starts-a-thread) and [PROTOCOL.md](docs/PROTOCOL.md#mail-in-smtp).
- **An organisation's own tools, run by the node in a container that reaches nothing.** A signed-in member of a role the app names (`keg.org_tools_by`) uploads a tool of JavaScript with `keg.org_tool_put`. The tool has a name beginning `org.`, a sentence, a schema for its arguments and code. The app's agent calls it with `thread.tool({ name: 'org.…', arguments })` and no function. Keg's SQL gives the code only to a step of a thread of that organisation, with a claim signed with the node's key naming the thread, the organisation and the code's hash. The node runs only that code, for that step, in a container made for the call. The container has no network and no volume, runs as nobody, has no capabilities, and is held to the time and memory a person set with `keg app org-tools APP on --env ENV` (5 s and 128 MiB a call, and 600 s a day, by default), of which one organisation may use a quarter of the day and two of the four calls at once. Its clock reads only the day, and nothing is kept between calls. Every upload, replacement and removal is an event with the code's hash, and so is every call. Capability file 023.
- **The Mac app has Access, Workspaces, Agents and Models pages, as the console has them.** Access: the connector door (its address, Open for Ten Minutes, Shut Now), sign-ins that wait (let one in by typing the code its app shows, or turn it away), everyone let in with what each has open (rename, revoke), the SSH door (on or off, its host key, open sessions with End), adding a key, making a token by hand (shown once to copy, never kept), letting a sign-in in as someone already let in (the node says what that does, and a second press says yes), client documents on or off, and where previews go. Workspaces: each one's state, owner, folder used against its limit, project, previews (public until they expire, private again, closed), repositories (added with the host's key shown first to check), limits for one or for new ones, sharing, and the record of what it ran, never what it printed; new, start, stop and remove. Agents: an app's threads in an environment, the stranded mark and Wake, a thread's events as written (an ask's arguments in full), Stop, and a dry Replay with Compare. Models: the models offered with their prices (cached input too), each limit with its note and Let It Go On, changing a limit (for an app, each organization's too), and today's spend by spender and organization. What a stranger wrote is shown as plain text, with characters that turn or hide text written out. Their new sentences are shown in English until they are translated. Asks are shown in a thread and not answered there: they are for the app's own people.
- **`keg setup server`: from a Linux server with Keg on it to a door an app can be let in at, as a checklist.** Run on the server, it prints a line for each thing the node looked at, each with a name that never changes, a state (`ok`, `to do`, `cannot tell`, `wrong`) and a sentence: the node's public name, whether its names lead here, what holds ports 443, 80 and the SSH door's, what of Keg's or a database listens on an address other machines can reach, the certificate, the doors' names, the image a workspace is made from, and the door tried from the node as an app would try it. It changes only what is Keg's own, each change shown and asked first (`--yes` for all): a drop-in of Keg's own unit for the public name (`--domain`), the names of the connector door and of previews, the workspace image, and a user for the SSH door's helper. It never edits the server's firewall, another unit, or what holds a port. `--check` looks only and ends with 1 while anything is left; `--json` is for a program. The console's Access page shows the same checklist, read only, on a server whose door has no name. [WORKSPACES.md](docs/WORKSPACES.md#setting-up-a-server-from-nothing) has the whole road and a table of what is open to the internet and what is not.
- **A workspace says how much of its folder is used**, against its limit, in `keg workspace ls` and `show` and in the console, where the node can tell. The driver reads its own filesystem's count; nothing in the folder is opened.
- **The console adds a repository to a workspace and ties it to a service.** For ssh nothing is added at first: the host's key is shown, and added only once you have given the key you checked. The Command page says what each organization of an app spent today where you set them a ceiling. `keg access ssh` says when the door's helper has no user of its own, and how to give it one.
- **Keg's SSH door: `ssh` lands in a workspace, and nowhere else.** `keg access ssh on` opens it on port 2222 (off until you do); `keg access add-key NAME < key.pub` adds a key as an identity; `ssh -p 2222 WORKSPACE@your-server` is a shell in a workspace that key's identity made or was given, `new@` makes one, and a command, `scp -O`, `sftp` and `-L` to the workspace's own ports work as they do anywhere. Only ed25519 and ecdsa keys are taken: no passwords, no certificates. Another's workspace, a name nothing has and `root` are refused in the words and after the wait a wrong key is. Your agent, your display, ports and sockets of the server, and forwards to anywhere but the workspace are refused. Revoking the key, stopping the workspace, taking a share back or `keg access ssh end SESSION` closes a session at once. The protocol is spoken by a program of its own with no rights, `keg-sshd`, which can only ask the node: the node never reads a stranger's SSH packet. `keg access ssh` prints the door's own key to pin. An RSA key is no longer taken by `add-key`.
- **Git in a workspace, a repository you give it, and a release proposed from it.** An agent at the connector door has `git_status`, `git_diff`, `git_log`, `git_commit` and `git_branch`; what it gives them is checked before anything runs, and nothing git could take for an option is taken. `keg workspace remote NAME add origin URL --key ENTRY` gives a workspace a repository elsewhere and a vault entry (a private key for ssh, a token for https) to push to it and fetch from it with: `git_push`, `git_fetch`, `git_pull`. For ssh the host is pinned to the key you confirmed by its fingerprint. The key is in the workspace for the one command and written down nowhere; a workspace granted a key can use it for as long as it is granted, so give it a deploy key. `keg workspace project NAME SERVICE` ties a workspace to the one service it may release, and `propose` builds a release from its last commit as an agent's: it waits for you wherever an agent's does, is handed no secret unattended, and says in the change set which workspace, connector and commit it came from. `needs` tells an agent what it asked for that waits. `keg workspace new --from … --key …` makes a workspace from a repository that is not public.
- **Previews: look at what a workspace serves, at a private address of its own.** `keg access previews keg-previews.example.net` says once where they are answered: a domain of your own that shares no parent with the node's public name (Keg refuses `pv.keg.example.com` or `keg-previews.example.com` beside `keg.example.com`, as a preview's page could otherwise set cookies for the connector door and every shared app); `keg workspace preview NAME PORT` (or an agent's `preview_open`) gives a port `https://<name>--<workspace>.keg-previews.example.net`. Another preview's page reaches a preview only as a person following a link, and a page of another site cannot post to the connector door. It answers only a browser you let in by the six-digit code its page shows (`keg access approve CODE`, or the console), to that one preview; a browser that was not let in never reaches the workspace. Keg's cookies are taken out of what goes on to the workspace, and the workspace's server can set none of Keg's names and none for a wider name. `keg workspace publish NAME PORT --for 2h` makes one public for a while and is yours alone; an agent can only ask. An agent reads what its server answers with `preview_fetch`, which asks that port and nowhere else. The console lists a workspace's previews and the browsers let in. See [WORKSPACES.md](docs/WORKSPACES.md).
- **Keg's model gateway is part of the node.** The node claims the calls it holds and reaches the provider itself, reading the key of each call's provider from the vault for that call alone; there is no `models` service to install, start or keep. A node that ran one stops and removes it at its first start, keeps its keys for the node, and says so once (its log, an event, `keg assistant model`). `keg system install models` says there is nothing to install, and `keg assistant setup` installs the assistant alone.
- **A model provider of your own.** `keg assistant provider add NAME --url URL --kind openai-compatible|openai|anthropic [--key-from-env-file PATH | --no-key] [--allow-private]`, `ls`, `rm`, `test` and `default`; `keg assistant model add PROVIDER/MODEL` with its prices or `--free`. OpenRouter, Azure OpenAI, a local Ollama, LM Studio or vLLM (Chat Completions), OpenAI's Responses, and Anthropic's Messages. The key is the vault's `keg/model/NAME`, for the gateway alone. A local or private address only for the one address and port a person allowed; on a Linux server that may be the server's own loopback. What each provider says it read from its cache is counted at the cached price.
- **Standard SDKs and agent frameworks reach the model through Keg.** An app's door and a work's door answer `POST /v1/chat/completions`, `/v1/responses` and `/v1/messages`, streamed or whole, and `GET /v1/models`, with the door's token as the SDK's key: only the base URL and key change. Each call is held, settled and limited as a call in Keg's own shape; a model not offered is refused in the SDK's own words; what Keg does not carry (images, audio, tools the provider runs) is refused plainly.
- **A workspace may be given the model.** `keg workspace model NAME on --usd-per-day N` (a person's) gives each new command in it `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL` and a token of its own as the SDKs' key, so an agent framework in a workspace asks the model with nothing set by hand. Its wall allows the node's door at one address and port and nothing else of the node's; it spends as `workspace:NAME`, held to its own ceiling. `off`, a stop, and its owner revoked each end it.
- **An agent's step through an SDK is counted for its organization.** The compatible endpoints take `Keg-Claim` as the native path does, sent as one of the SDK's default headers, so per-organization ceilings hold for it too.

### Fixed
- **Security: `keg sandbox` is walled to the internet.** It ran on the node's own network, where it reached whatever the node listens on at its loopback (its API, the model's door, a database). An agent's sandbox, and a person's by default, now reach the internet alone; a person who wants the node's network says `keg sandbox --host-network`.
- **Security: a container's wall is never opened to a loopback or link-local address.** `egress_allow` refuses `127.0.0.0/8`, `169.254.0.0/16` (where a cloud server's metadata gives out its credentials), `::1` and `fe80::/10`, in a sentence that says why.
- **Security: a message is a repeat only by its own bytes, for the address it came to.** It was named by its Message-ID and the sender's claimed domain, neither of them verified, so whoever sent first with a real message's id had that message dropped as a repeat.
- **A hook's body and a message's attachments reach the app whole.** They were handed to the database as an option of psql's, which Linux holds to 128 KiB; they now go on psql's input, as hex written once as it is sent. A hook takes 4 MiB; a message keeps an attachment of 4 MiB (8 MiB of one message's).
- **Mail and hooks hold what arrives apart, and only so much at once.** Each has a pool of its own (mail 128 MiB, hooks 64 MiB), held only once a request has passed the cheap checks, as its bytes arrive (never from a length promised), and to a share for each network and address; past that, a mail server is told `451` and a hook's sender `503`, both to send again later.
- **Security: what arrives from outside cannot fill the disk or spend an organization's money.** Each hook's or mail address, and each app in all, take so many bytes a day (64 MiB and 256 MiB unless the app says otherwise); past that, a hook's sender is told `503` and a mail server `452`, and nothing is written. What was received is kept 30 days unless the app says otherwise, then goes with its event and its attachments. An organization's deliveries and messages start at most 200 threads a day; past that, each is written and starts none. An app says these with `keg.inbound_limits` in a migration. A verified hook delivery no longer pays its sender's network's count, so GitHub's bursts are not refused; a mail conversation has 15 seconds and 20 commands to name an address, and with every place held a newcomer takes the oldest idle one's (or is told `421`), so idle conversations cannot keep mail out. When an app's addresses cannot be read, a sender is told to try again (`451`, `503`), never that the address is no one's; the node reads them one request at a time. An attachment's long name, a body Postgres's JSON refuses, and a long Stripe id no longer make a delivery fail for good.
- **Turning an organisation's tools on fetches their image then**, and says so when it cannot be fetched, rather than at a tool's first call.
- **The Mac app's Models page has the providers**: listed, added with a key read from a file you choose (sent once to the vault, kept nowhere by the app), made the default, and removed.
- **Security: a command an identity left running in a workspace is stopped when it loses that workspace.** Un-sharing a workspace, revoking an identity or removing its key ended its sessions and the calls it was waiting on, but a command left running by the connector door's `run_start` ran on. Who started each run is now written down before it starts, where it outlasts the node, and losing the workspace ends every run that identity started there; the node looks again each minute and after it starts.
- **A call whose caller went away stops.** A call whose answer was not taken to its end (the caller closed its connection, or stopped reading) is ended at the provider, settled at what it used, and gives back its place at once, in every shape; a caller gone while it waits for a whole answer is noticed too.
- **One set of bounds for every call at every door.** What the tools' schemas describe is checked in the one check every call passes, and every request body is looked at as bytes for how deep it nests and how many values it holds before any of it is built.

## [0.14.0] — 2026-11-26

### Added
- **An agent in an app asks the app's own people.** `thread.ask` in three kinds: approve one exact call of a tool, choose one of a few, or answer in words; addressed to roles or users of the thread's organization, waiting up to 30 days, answered once. The app's pages read `db.asks()` and answer with `db.answer()`; only a person who signed in answers (never a job, a tool or a worker). Keg tells those asked with `keg.ask.asked`, `keg.ask.answered` and `keg.ask.expired`.
- **A tool declared `changes => true` now runs, on a person's approval of that very call, once, as that person.** The person is shown the tool's own words filled from the call, never the model's; other arguments, a second run, an expired approval or an approver who lost the role are refused.
- **A thread waits.** `thread.sleepUntil(time)`, `thread.waitFor({ until, event, about, message })` and `thread.listen`: woken once by whichever comes first, across restarts of the app and the node. An event wakes a thread only if everyone who may read the thread may read the event. `keg.thread_message` sends a thread a message.
- **A thread starts a child agent**: `thread.spawn(agent, input, { budget })`, its budget carved from the parent's, the parent woken with its result. A thread that started several is told of each once, as each ends and in any order.
- **What wakes a thread has room of its own.** A thread keeps 50 messages unread and takes 20 within a minute from one sender, and messages never keep out an answer, an event, a child's end or a person's wake. A thread that more events came for than it keeps unread reads `wake {why: 'missed'}` at its next step. `keg app threads wake` says when it did not wake a thread (no worker of the app has taken the wakes it was given), and writes nothing then.
- **What a person approves hides nothing.** The tool's sentence ends an argument it cut with `…` and writes out characters that turn or hide text (`\u{202E}`); an approval is asked only of arguments the tool's schema names, with those it requires; the ask carries every argument, for the app's page to show in full beside the sentence. `ask` and `approved_by` on a `tool.call` are Keg's alone. An ask expires no later than its thread's own time runs out, so an agent that waits days for a person needs `max_minutes` to match; a wait for an ask that is no longer open ends at once; and an answer to a thread that ended meanwhile is told the ask was withdrawn.
- **`keg app threads wake APP ID`** wakes a thread; `keg app threads` marks as `stranded` one that is ready with nothing to wake it; `keg app threads APP ID` shows a thread.
- **`keg work approve N`, `keg work reject N`** answer a piece of work by its own number, and `keg needs` and `keg work show` name them. **`keg work evidence N [CHECK]`** prints what a work's checks printed.
- A piece of work is handed the Keg skill under `/keg/skill`, the guide to an agent in an app among it.
- **A thread is replayed, dry.** `db.fork(thread, at, { vary, budget })` makes a new thread with the same record up to an event, which goes on by itself with other instructions or another model; `db.compare(fork)` says then and now; `db.evaluate` forks up to twenty at once. Keg holds a replay dry as far as it reaches: its tools' transactions are read only, a tool that changes things is recorded as what it would have done, it asks no person and starts no child, no `keg.thread.*` event is written for it, and `keg.tx` in its handler is read only. Anything else a handler does (a mail, a request to another service) is the handler's to hold: make it in `thread.tool`, or check `thread.dry`. Replaying is for the roles a migration names with `keg.agent_replay` (administrators by default) and the node's person (`keg app threads replay`, `keg app threads compare`); a replay is read only by one of them who may also read the original. A fork spends from a budget of its own, five cents unless more is asked.
- **Each organization of an app is counted, and held to a ceiling of its own when you set one.** `keg assistant limits app:APP/ENV --per-organization-usd-per-day N`. The app's door checks a claim Keg's SQL signs for each step of a thread, so an app cannot count one organization's spend under another; `keg assistant usage` lists organizations under their app, and what dry replays spent as evaluations.

Tokens are kept as hashes only. An app sends your browser to a page that shows a code and waits: nothing is typed there, and you let the code in from a place you trust (`keg access approve CODE`). The approval names the host the app asks to be sent back to before what the app says it is, and a host Keg does not know needs a second yes (`--unknown-redirect`). `keg access token NAME [--days N]` makes a token by hand for a client that cannot sign in. Fifteen tools: `workspace_new|list|show|stop|remove`, `files_write|read|list|search|patch`, `run`, `run_output`, `run_start|status|stop`; a reply is at most 30,000 characters and says how to read the rest; `run` waits 30 seconds (120 at most) and then hands back the run's name instead of failing. Files are read and written by a script run inside the workspace as its user: the node never opens a workspace's file. A command left running keeps its workspace from being stopped for being idle (`keg access keep MINUTES`, two hours unless said). Everything else at the door's name is 404, and nothing of the node's own API is reachable from it. See [WORKSPACES.md](docs/WORKSPACES.md). Previews, git and `propose` and the SSH door are not built yet.

The agent names a check and nothing else: the node takes its own snapshot of the tree (as it takes every commit of a work in, into a store of its own that is removed when the run ends: no branch is moved and nothing is added to your repository), and reads the check from that snapshot. A round runs 20 of them, one at a time, for 30 minutes in all, and is told 1 MiB back, its snapshots 1024 MiB in all, unless a person says otherwise (`keg work self-checks [--runs N] [--seconds N] [--output-kb N] [--snapshot-mb N]`; `--runs 0` turns it off). ### Added

A check names at most four, and needs a runtime agent that says when a command's output was cut: with one from before, the verdict is `error`, naming the restart; its instances are made under its turn at a Postgres of its own, so at most two checks have either at once and a third waits in order; one whose image is not here is the verdict `error`, one that stops or is not ready in 60 s fails the check with its last line; each is removed when the check ends and what a stopped node left is removed as it starts. Events: deliveries backing off with Skip, failed ones with Retry, the timers set (at most 50, and how many more), and what finished deliveries said, as text. Apps: jobs being retried with their last error, names no worker takes, indexes still being built, a person's Retry Failed, and what an app is given only when next deployed. Work: a check that could not be run is shown as failed with its reason, and each check's tests against the round before, as printed. The containers list and a container's overview say which of its ports this Mac does not reach, and where it reaches them on another number; the first page says which ports on this Mac lead to the node, as `keg vm status` does. Removing anything starts on Cancel.
- **A query service, from outside.** `extensions/query` keeps each event it is told of (work, change sets, and SupportDesk's tickets and ratings where that app is) in DuckDB on its volume, and answers SQL that only reads on this computer's port 8224: a `POST` to `/query` of `{"sql": ...}` with the header `X-Keg-Query: 1` answers JSON, and its page shows a table. All it holds is read with a key a person sets (`keg system secret query QUERY_KEY`, at least 32 characters). DuckDB is opened locked, so a query reaches no file, network or extension, calls only a short list of table functions, and runs in a transaction that is rolled back. An answer is held to 10,000 rows, 100 columns, 8 MiB, and each value that is not a number or a time to 4 KiB of its text (a nested value as DuckDB writes it, not JSON); a query is answered from a copy of what it reads, made at most every 2 seconds, and says as of when (`as_of`), in a reader, a process of its own that is killed when its query runs on past its 10 seconds, whatever it calls, so that nothing else is lost and the events go on being kept; four queries run at once, one for each organization of each app, and a token for one organization asks at most 20 a minute (429 with `Retry-After` past either). An event to be kept while the databases' process is started again waits for it, within its delivery's hold, so no try is counted for that. It has 1024 MB, and the README says what of it each process takes and how much of its volume the copies may. It keeps 30 days and 384 MiB of events, the oldest going first, held in batches within DuckDB's memory; past its size and unable to prune, it keeps nothing more of that part and says why.
- **A NATS service, from outside.** `extensions/nats` runs a NATS server with JetStream on port 4222 and puts each event it is told of (work, change sets, and SupportDesk's tickets where that app is) in the stream `KEG` as `keg.<type>`. Readers connect as `reader` with a password a person sets (`keg system secret nats READER_PASSWORD`); until one is set, no reader is let in. The password is an operator's: it reads every organization's events of a bound app. Readers are in an account of their own, with a stream of their own, held to 32 consumers, 64 connections and small messages, and cannot publish, purge or reach the service's stream. Its page, on port 8222, lists the last it published, and says when the readers' stream had to be made again, empty.
- **Install a service from a folder in the console.** "Install from a folder…" on the Keg services page asks each item in the node's words, with nothing ticked that reaches past the service's socket, and builds it, with a way to call the build off. A service's secret is set there in a password field, sent to the node and never shown again; "Stop asking" (and `keg system decline <name>`) stops offering what a person left out, until the service is installed again with different asks.
- **Timers and results on Events.** The console's Events page shows the timers services set and what each finished delivery returned; `GET /v1/deliveries` gives each finished delivery's `result`.
- **An app's binding says which pages are the app's.** `GET /v1/bind/<name>` of an app's events gives `origins`, the exact origins (scheme, name and port) of the pages the node serves for that app's services. A service trusts a page as the app's only by these.
- **A token for an app, and tokens for one organization.** A bind to an app's events with `token = true` in the manifest has the node make a token for that service and app, given to the service with its binding and to the app's servers as `KEG_SERVICE_<NAME>_TOKEN`, with `KEG_SERVICE_<NAME>_URL` (the address a browser opens the service on) and `KEG_APP`, when the app is next deployed; `keg system ls`, the console and the install and removal answers say which apps are yet to be given it. The token reads every organization's content the service holds, so it never goes to a browser: the app's server makes a token for one organization, for at most 15 minutes (`v1.<payload>.<mac>`, `docs/PROTOCOL.md`), and hands that to its page. It is a bearer token: whoever holds it can use it until it expires, from anywhere, as it is bound to no origin. The query service keeps each organization's events in a database of its own (at most 64 per app, given by recent use: one that wrote nothing for 7 days gives its place up, and one given a place is filled from the app's own database) and answers such a token from it alone, and of them only those for every member: an event the app sent to some users or roles only is read with the app's own token, never through a page, in this version (each relayed app event carries `audience` and `about` from its row, which NATS passes on as they are; an organization given a place is filled with only such events too); it takes the app's own token only from a request no browser made. A bind with no `token` gives the app nothing: NATS's asks for none. A service keeps organizations apart by a relayed app event's `organization`, which, as in 0.10.0, is what the node read from the event's row (`keg.events.organization_id`, which the app's capability layer sets from the actor), never what the app wrote in its payload.
- **`@keg/app` for services and their apps.** `@keg/app/node` gains `hostAllowed(host)`, the check of `Host` both services use; the new `@keg/app/service` gives an app's servers `serviceFor(name)` (its token and address) and `serviceToken(name, { org, ttl })` (a token for one organization).
- **`docs/WRITE-A-SERVICE.md`**, how to write a service from outside, with a checklist, and `docs/PROTOCOL.md` gains bindings, a service's own events, timers, an app's events and pages.
- **Who is sent an app's events, said one way only.** `keg.expose_events_to(types => ..., roles => ...)` sends them only to those roles, and `keg.hide_events_from(types => ..., roles => ...)` to every member but those; `keg.expose_events(types, roles)`, which took the roles not sent them and was read the other way round, still works. `keg.off(type, job)` takes back a `keg.on`, and says so if there was none.
- **An app reads its own events, each member only those meant for them.** `keg.emit(type, payload, audience)` records who an event is for: `'{"organization": true}'`, `'{"roles": [...]}'` (at most 20, each a plain word) or `'{"users": [...]}'` (at most 100, each a member of the organization). It fails closed: a null audience, or `to: undefined` or `null` in `@keg/app`, is refused, never read as the whole organization; that is said only by leaving the audience out or naming the organization. The view `keg.my_events` (id, type, payload, at, actor, about) gives the member acting their organization's events of an audience they are in, behind a security barrier, read newest first by an index and a page at a time by `(at, id)`. Organization and audience decide who may read an event; `keg.expose_events*` decide only what the realtime gateway pushes, so what is pushed is always among what may be read, and `keg.visible_events` now honours the audience too. A job, as the organization's `system` actor, reads what is for the whole organization and what names `system` among its roles, never what is for users. `keg.emit(type, payload, audience, about)` says what an event is about (`ticket/42`, at most 200 bytes, refused if longer), in a column of its own and never from the payload, so a long `payload.subject` is only a payload; an index makes "events about this, newest first" cheap, and adding the column writes no row again. `@keg/app` has `db.emit(type, payload, { to: { roles } | { users }, about })` and `db.events({ type, about, limit, before })`, which reads each page, the first or one far back, from the index whatever Postgres's statistics say (with sorting turned off for that statement alone), and the node has Postgres look at `keg.events` again once it has built one of its indexes, so the columns 008 adds have statistics. The relay to services from outside is not held to an audience.
- **`keg app jobs`** lists an app's jobs that wait, run or failed, with their attempts, when each runs next and its last error, made safe to print (`--env`, `--failed`, `--json`); `keg app jobs retry APP ID` and `keg app jobs retry APP --failed` put failed jobs back to waiting with their attempts reset. `keg app show` and the console's Apps page say how many are being retried and the last error, and name a job that no worker has taken for five minutes ("is its handler registered?"); the console has a Retry button. Like `keg app show`, these are a person's: an agent is refused them.
- **A check may ask for a database of its own.** In an app's `keg.yaml`, `checks: [{ name: e2e, run: "npm ci && npm test", db: true }]` runs the check against a Postgres of its own: a container started for it from the image the node's shared Postgres runs (pinned, so nothing is fetched; a node that has never run Postgres fetches it by a digest written in Keg, never by its name), with 256 MiB of memory, 1 GiB to write and its newest 10 MiB of output kept, walled so that it makes no connection of its own, at its own address, with no port published. Containers on the node's bridges cannot reach it. Work machines and other containers that share the node's network can reach its address over TCP: only its password, 192 random bits given to that check's command alone, keeps them out. Without it, a hostile piece of work can at worst use up that server's connections or memory and so make another work's check fail, never pass; the node's shared Postgres is open to them in the same way. Not built yet: a unix socket in the work's own mount instead of TCP, or work machines on a bridge of their own with one opening for each check. In it are the app's capabilities and the work's own migrations, at the commit checked, and the check is given `DATABASE_URL` (with `KEG_ENV=check`, `KEG_SERVICE` and `PORT`; no secrets, no data and no realtime of any environment). It is ready in about a second, and says so in the check's output. A migration that fails fails the check, with Postgres's words. The container is removed when the check ends, and what a node that stopped meanwhile left is removed when it starts. At most two run at once; a third waits up to ten minutes, and is then given back to be run again, never failed for waiting; those that wait have their turns in the order they came. One that runs out of memory or is not ready in 90 s is started again, three times in all. A node that cannot run one at all (no loop devices, an agent from before, which kegd asks to be restarted, or an image it cannot fetch or that is not the one pinned), or one that did not start three times, gives the check the new verdict `error`, with why, which holds the work at the gate rather than trying again. The evidence says "with a database of its own".
- **A tenant table says what each command allows.** `keg.tenant_table('app.ratings', update => false, delete => false)` (and `insert => false`) turns those commands off for every role the app connects as, its jobs among them: an UPDATE or DELETE touches no row, an INSERT is refused. Called again it keeps what it is not told: a command turned off stays off until a later call turns it back on by name (`update => true`). Called with the table alone the first time it is as before: every member of the organization may read and write every row unless a restrictive policy says otherwise. The guide and `keg app new`'s migration say so, and that a restrictive policy `FOR ALL` covers `SELECT` too.
- **The gate shows how many tests each check ran, against the round before.** The checks service reads the counts that node --test, cargo test, pytest, jest, vitest and go test -v print, as well as JUnit and TAP, into its record ("e2e: 41 passed, 0 failed"); what it reads never decides whether a check passed, and a number past ten million, or a sum past it, is no count: it is shown as unknown, and nothing a check prints can make the checks or `keg` overflow. The count is kept with the record as numbers (`tests` in its evidence), never read back out of a summary a check's name could fake, and is shown "as printed". `keg work show` and the console's work page say "e2e: 41 tests (was 41)", as numbers only, so that tests asked for in a note and not added show at a glance.
- **Cleaning up, and what building keeps.** `keg cleanup` shows what is on the node's disk by kind, with sizes (layers images share counted once), and item by item what a cleanup would remove and why each thing is kept or not; `keg cleanup --apply` removes it and says what it freed. What is always safe goes: the images of builds older than the newest 5 of each service, checks' containers that have ended, and layers and blobs nothing refers to. Only when asked: `--works` (the machines and folders of finished pieces of work whose days are up), `--images` (images nothing uses, pulled or built by a person), `--containers` (containers a person ran that have ended), `--build-cache`, and `--volumes NAME…`, each volume by its name. `keg rmi --damaged FILE` removes an image record that cannot be read, as `keg cleanup` names it. `--dry-run` is what it does without `--apply`; `--json` gives it whole. Nothing that runs, that a change waiting for approval would deploy, that a rollback goes back to, that a piece of work at its gate asked about, that a machine or a service from outside is of, or that is the shared database's image is ever removed. Only a person may: an agent is refused all of it, and a service with it. `keg system keep builds N` and `keg system keep work-days N` (0: as soon as it is finished) say how much is kept, and `keg system keep works ask|auto` whether Keg asks before clearing finished work (`ask`, the default) or the node clears it by itself. The console and the Mac app have a Storage page, with the disk by kind, these settings, and Clean up, which shows exactly what goes and what it frees before anything does.
- **The node cleans up after itself.** After each build and once a day it removes what is always safe to remove, from a day after it first looks: until then it only says what it would remove (`keg cleanup` shows when it begins). Keg asks before clearing finished work: a finished piece of work (merged, or turned down at its gate) is shown as one that can be cleared 7 days after the node saw it finish, and its machines and folder go only when a person ticks it (or turns `keg system keep works auto` on). Its branch, evidence, notes and what it changed stay, and once it is cleared it cannot be taken up again. Its folder is removed only where it was made, never through a link, and not while any container has it. A layer made in the last hour is never taken, so nothing a pull, a build or an image sent from another node is still using goes. On a Mac the node then tells its disk which blocks are free, at most once a day, so the space comes back to the Mac; elsewhere only with `keg cleanup --apply --trim`.
- **A disk nearly full is said.** From 85% full the console's first page, `keg system ls` and `keg vm status` say so and how to free space; at 95% a build or a `keg pull` is refused before it writes anything, with how to free space, rather than failing part way. `keg vm status` shows how much the disk image takes on the Mac beside what the node uses of it.
- **A cleanup knows what works were handed and what their checks ran against.** Storage counts the files handed to pieces of work as a kind of its own ("Files handed to works"); they go when their work is cleared, once nothing has them, and never before, and a finished work's item counts them. A check's own instance of a service and its volume are kept while the check has them; one that has ended and that its check no longer has goes with the checks' throwaway containers.

### Changed
- **The Mac's Linux machine is smaller and starts sooner.** Its image is made of only what the machine runs, from a root of its own (`RUNTIME_PACKAGES` in `Scripts/build-vm.sh`, which says who needs each), where it was the whole container Keg is built in, with its C compiler, binutils, make, Perl and rsync: 17 MB to download where it was 62, and 50 MB in the VM's memory where it was 189. On an Apple M4, six boots of each: the API answers 0.8 s after `keg vm start` (median; 1.4 s before), and the VM uses about 160 MB where it used about 300. It ships 36 Alpine packages where it shipped 71, and 13 sources under the GPL or LGPL where it shipped 29 (3 of them under version 3, where it was 11: no cpio, make, rsync, gmp, mpfr, mpc, libidn2 or libunistring); the GPL source a release carries for them is 43 MiB where it was 225. A throwaway node ran on it every path that runs a program of the image: a published port, a container as another user, `keg build`, Compose with a named volume, Keg's own services, a service from outside built behind walls on spaces of a fixed size (`extensions/query`), shared folders, an app on the shared Postgres, a piece of work's machines, Rosetta, the SSH agent, Docker's API, and a stop and start with its data kept. The release checks the image holds no compiler or build tool and stays under 20 MiB packed, 56 MiB unpacked.
- **On an agent's credential, `keg machine shell NAME -- <command>` and `keg sandbox` work.** They opened a session, which an agent may not; they now run the command to its end through the calls an agent has (as `keg_machine_run` and `keg_sandbox` do), with its output and exit status. An agent's machine shell runs one command at a time; its sandbox has nothing of the computer in it. `keg machine create` on an agent's credential asks the Mac to share nothing, as `keg_machine_create` does: the folder must be one the node gives to agents.
- **Faster where the node is asked most** (`docs/PERFORMANCE.md` has every number, how they were measured, and how to measure again with `Scripts/bench.sh`). On a Linux node with 200 containers: `keg ps` takes 3.8-10.4 ms where it took 14.7, `GET /v1/containers` 2.1-3.7 ms where it took 12.9 (846 a second from 8 clients, where it was 296), Docker's `containers/json` 6.9 ms where it took 15.3, and a refresh of the Mac app costs the node 12-20 ms of processor where it cost 66 (the console's, 10-14 where it was 45). kegd keeps its connections to the runtime agent, so a question of it takes 9-19 µs where it took 70-120. Claiming a delivery with 2-3 thousand waiting and 9 thousand done takes 0.30 ms where it took 26.4, and finding when the next is due 0.13 ms where it took 18.2. The Mac's forwarder asks the node for its ports once and is answered when they change, where it asked ten times a second: about 20 ms of the node's processor each 30 seconds where it was 230-310. `keg logs -f c | head` ends once `head` has its lines.
- **A walled container is reached by the node from an address of its own** on the walled bridge, the last of the walled range (`10.89.255.254` unless the range moved), which is never handed to a container. A walled container's own rules let its published and reached ports in from that address alone, so they keep containers on the node's bridge out even while the node's own rules are being made again, and they are made before its link is up. A service from outside sees the node's connections come from that address.
- **The console refuses a request another site's page sends**, by its `Origin`, whatever it carries; a request with no `Origin`, as `curl` and `keg` make, is answered as before.
- **The Keg License.** Keg is closed source and free to use under the Keg License (`LICENSE.md`, `keg license`), which comes with the app, the `keg` command, the disk image and each release; `keg license --third-party` lists the software by others in Keg. It was in 0.10.0's files and is said here.
- **A new container may no longer be named `machine-work-…`**, through `keg run --name` or the Docker API: those are the names of the machines Keg makes for pieces of work. A container that already has such a name is left as it is.
- **A relayed app event carries the organization the node read from its row** (`organization`, from `keg.events.organization_id`, which the app's capability layer sets from the actor), never what the app wrote in its payload, so a service may keep each organization's events apart by it.
- **The Mac app no longer asks the node for everything every 2 seconds.** It holds the node's log of events open, as the console does, and asks again only for what an event concerns, and only where it is seen: the section shown and the sidebar's counts, or with no window only what the menu bar's item shows. Charts are read every 2 seconds only while they are in front; everything seen is asked again every 30 seconds only while the window is in front; a node that does not answer is asked a second later, then twice as long each time up to half a minute. While the node is at rest the log is not held open, since a held request counts as work and its VM sleeps only with no connection open: it is looked at every 15 seconds and let go at once, and while the VM sleeps nothing is asked at all. Storage's report, which the node walks its disk to make, is asked for only while Storage is shown: when it opens (at most once a minute), after a cleanup or a change to what is kept, and when the log says something that held space went, at most every 15 seconds.
- **An app's events reach a service in the order they were read**, for each app and environment: a later one is not claimed while an earlier one waits, runs or backs off, and one failed for good holds nothing back. A service is still told of an event again after a hold runs out, so it is still safe to be told of each twice.
- **What a service held is waiting again at once when a person ends its run** (stopped, removed, installed again) or the node starts again, its try not counted, and a claim that was waiting as it stopped is given nothing. Before, each waited out its hold of 60 seconds, and an app's next event could go ahead of it. When its run ends by itself (it exits or crashes) holding a delivery, the try counts, so an event it dies on every time fails after its fifth try and the app's next events go on. `keg events skip <delivery>` (and "Skip" on the console's Events page) lets a person fail a waiting one sooner. How far behind a subscriber may be on an app's events is counted for each environment, so `local` cannot starve `prod`.
- **A name in `local` that is an app's service is that service's, and never a person's container of the same name**: while the service has no port, the name leads nowhere.
- **The install question says what is true** of a service bound to an app's events: that it holds every organization's content of what it hears, who may read it, what a token for the app is for and when it is given, and that a published port is reached by any program on this computer.

### Fixed
- **Two nodes on one Mac no longer hand out each other's addresses.** Each node's VM serves names on 7380 and 7443, and the Mac's forwarder only logged when one was taken there, so the second node's `KEG_REALTIME_URL`, its apps' origins, its console link and its "Try it" and "Open" links led to the first node, with what they carried (a signed-in user's session token, the console's link). Now a port of Keg's own that another program holds on the Mac is opened on the next free one (kept in `~/.keg/runtime/mac-ports.json`, so links stay the same), the forwarder tells the node what leads to it (`PUT /v1/reach`, a person's alone), and the node hands out only that, and nothing before it is told. `keg vm status` says which ports the node got and why. A port asked for by number is never moved: `keg ps`, `keg ports` and the console say when the Mac does not reach it. An app keeps an address it was given until it is next deployed, which `keg app show` and the console say. See "Where a node is reached" in `docs/PROTOCOL.md`.
- The Mac app no longer ticks, for a person installing a service from outside again, what reaches past its socket (a port of this computer, the internet), as the command line and the console do not. It did in 0.10.0.
- **Each environment of a service keeps its own way in.** A release approved into `staging` no longer takes `localhost:3000` from the same service in `local`, after which every deploy to `local` failed until staging was stopped by hand. The first environment of a service to be deployed has the port its `keg.yaml` names; another environment of the same service is given the next free port, keeps it, and is reached by its name (`web.staging.keg.localhost`) as before. `keg services` shows each one's port, and on a node where another environment already holds the port `local` names, says which and the commands that give `local` its port back (an upgrade does not move it). Another service that names a port already held is still refused.
- **`GET /v1/apps/<app>` no longer fails while the app is first deployed.** The app is bound before its database, roles and grants are made; a reader meanwhile (the console asks every few seconds) was answered 500, and could make the app's password itself, beside the deploy. An environment whose database is not made yet is shown without jobs, and nothing is made by reading. Also: `keg ps` says how many app containers it left out and that `keg ps --apps` shows them; `keg services` says what runs in the other environments; `keg events` says its times are UTC; the build agent is told to install the project's dependencies and run its checks before it commits, and never to commit with a test it knows fails.

### Upgrading from 0.10.0
- **Restart the runtime agent on a Linux node.** The agent that runs containers now speaks protocol 4, where 0.10.0's spoke 2. A node upgraded without restarting it goes on with the old one: containers keep running and most things work, but a cleanup, a check with a database, a check with services, and reaching a walled container are refused, each with a message that names the restart. `sudo systemctl kill kegd` restarts it (systemd starts kegd again, with a new agent): every running container stops; Keg's services and machines start again, other containers do not. On a Mac, Stop Keg and then Start Keg in the app (or `keg vm stop` and `keg vm start`); that too stops every running container.
- **The node removes nothing by itself for a day after its first start on this version**, and only says what it would remove; then, after each build and once a day, it removes the images of each service's builds beyond the newest 5 that nothing needs, and what is otherwise always safe to remove. To keep more builds, say so before then: `keg system keep builds 20`. `keg cleanup` shows what would go and the day it begins. Releases stay in the record; a release whose image has gone can no longer be promoted or deployed again, but what runs and what a rollback goes back to are always kept.
- **Clearing finished work is off.** The node never clears a finished piece of work by itself unless a person turns it on (`keg system keep works auto`); until then it lists it as work that can be cleared, and a person ticks it.
- **A work's machine that was running across the upgrade has no record of the container Keg made for it** until it is started again: Keg now finds a work's machines by that id, never by a name. Until then, clearing that work leaves its folder and says why ("Keg has no record of the container it made for …"); stopping and starting the machine, or the node, records it.
- **Turn the assistant on, if wanted.** Nothing of it runs after an upgrade: `keg assistant setup --env-file <path to a .env>` reads `OPENAI_API_KEY` once, seals it for the model gateway, and installs and starts the gateway and the assistant. Its spend is held to $5 a day for the assistant and $20 for the node unless changed with `keg assistant limits`. What it reads is sent to OpenAI, log lines among it; anyone with the console's link can read its conversations and confirm the changes it proposes, so treat that link as the node's key.
- **The node's own store gains, as it starts:** new columns of deliveries, evidence, finished work and backing services (a backing service from before is a person's); the tables `confirmations`, `runs`, `run_steps`, `conversations`, `secret_marks` and the model ledger's; and the table of bindings is made again, in one step, to take the kinds `model`, `tools` and `runs`. An app that uses events or jobs is given capability files 007 to 009 at its next deploy, or sooner, when the relay next reads its events (008 adds two columns to `keg.events` without writing a row again; the node builds its two indexes afterwards, concurrently, and `keg app show` says while it does).
- Where a Mac's port of Keg's own (7380, 7443 and the rest) is held by another program, the node is now reached on the next free one, kept in `~/.keg/runtime/mac-ports.json`; an app keeps an address it was given until it is next deployed.
- **A service from outside installed before this version (query, NATS) is to be installed again from this version's folder** (`keg system install <folder> --replace`, or Install from a folder… in the console). Until it is, a check that names it in `services:` fails, the instance answering the check "only names of this computer are answered" (its own copy of `@keg/app/node` does not know the address a check gives it, `KEG_ADDRESS`), and works are handed none of its instructions (`docs` in its manifest is read as it is installed). Installing it from another folder removes its volume and secrets, and with them what it held: the query service then holds only the events of after it (the relay sends a newly bound service none from before, so a Reports page built on it starts again from nothing). Set its secret again, and deploy each app bound to it again so that it is given its new token. (Said after the release: the notes as released left it out.)

### Going back to 0.10.0
- **Not supported once the assistant or the model gateway has been set up.** 0.10.0 does not know Keg's services `models` and `assistant`, nor bindings of the kinds `model`, `tools` and `runs`, which it answers as bindings that are not there.
- Otherwise: 0.10.0 leaves the new tables and columns of the node's store as they are, and does not read them: conversations, runs, proposals and the model ledger stay, unread, until this version is installed again. An app's database keeps what capability files 007 to 009 made (who each event is for, what it is about, `keg.my_events`, the indexes), which 0.10.0 leaves as they are. The steps for 0.9.0 below (services from outside, `remove-walls.sh`) apply only when going further back.

## [0.10.0] — 2026-11-22

### Added
- **Work and gates.** `keg work new` begins a piece of work in a project, on a branch and in a worktree of its own; agents take it through build, test and ship in a machine of their own, and each stage keeps what it found as evidence. A gate waits for a person: `keg needs` lists what waits, `keg gate approve|reject` answers, and `keg work send-back` sends it back with what is to be changed. Nothing is merged until a person approves. An agent sees none of this and answers no gate.
- **A log of events.** Every change the node makes (work, stages, gates, evidence, change sets, services, apps, containers) is written as an event in the same transaction as the change. `keg events` reads it; `keg events failed`, `keg events retry` and `keg events timers` show what Keg's services have yet to do. The console and the Mac app have an Events page, and refresh when something happens.
- **App capabilities.** A `keg.yaml` with `app:` and `uses: [data, identity, events, jobs, realtime]` gives an app a database of its own in each environment, in which tenancy is the database's to keep: sign-in, sessions, organizations and members; events and jobs, at least once; and a realtime gateway that sends each subscriber what its user may read. `keg dev` runs one, `keg app ls|show|new|stop|org` looks after them, and `@keg/app` is the library.
- **Keg services.** Keg runs services of its own on the node, each in a container with a socket and grants of its own: the console, the checks that the test stage asks for, and the realtime gateway. `keg system ls`, `install`, `start`, `stop` and `rm` look after them.
- **Services from outside.** A folder with a `keg.service.toml` is installed with `keg system install <folder>`: a person is asked about each thing it asks for, in plain words, and it holds only what was allowed. It runs pinned by digest, behind walls: no capability, no network but its socket (or the public internet only, if that was asked and allowed), memory, processes and disk capped, a volume, secrets and ports only through bindings of its own, at most 16 connections and 8 requests at once. It can be told of events, write its own, set timers and hear an app's events. Building one from its folder on the node is off until a person turns it on with `keg system builds on`; off, a service names its image by digest (`image = "…@sha256:…"`). A node needs loop devices and `mkfs.ext4` (e2fsprogs) to run them; one without says so and refuses them alone. `docs/PROTOCOL.md` is what such a service may rely on.
- **The console has two modes**, Containers and Builder, with a guide through both in ten steps; `keg example hello-keg` makes a small project to try them with.
- **The Mac app** has the same two modes and guide, and new sections: Needs you (pinned, with its count), Work with Approve, Send back and Reject at a gate, Keg services with the question of what each asks, Apps, and Events.
- **The source of the GPL and LGPL software in Keg**, the kernel and the Alpine packages of the Linux machine, is published with each release, as `keg-<version>-gpl-source-kernel.tar.xz` and `keg-<version>-gpl-source-packages.tar` (`Scripts/gpl-source.sh` makes them from the image built).

### Changed
- What a request names as a number (a CPU limit, a timeout, a duration, a recipe's minutes) is refused or held at its most when it is too large to hold, never a panic; a release build checks every sum for overflow.
- A panic while the control database is held fails that request alone: the node goes on.
- **An app's own transactions left idle are ended.** The roles an app connects to its database as have `idle_in_transaction_session_timeout` set to 10 minutes: a connection left idle inside a transaction for that long is ended by Postgres, and its transaction rolled back. One left open would hold back that app's events.
- **A Dockerfile or `.dockerignore` larger than 1 MiB is refused**, before more of it is read, by every build: a service's, and a person's own `keg build`, `keg up` and `docker build` alike.
- **What a request sends is held to a size.** A request to the Keg API, the console or the Docker API whose body is JSON is read to 1 MiB (evidence, whose body is kept to 1 MiB and cut past that, to 8 MiB). A blob or a volume's contents sent to the node is written to disk as it arrives, up to 64 GiB; a build context or an archive sent into a container through the Docker API, up to 16 GiB. A request past its limit, whether it says so or turns out so, is answered 413 with a sentence that says the limit, and its connection is closed as soon as that answer is sent, so nothing more it sent is read, as a body or as a request.

### Fixed
- One request could make kegd, or `keg ui` and `keg files mount`, end: the HTTP library they use read what was left of a body it did not need into one buffer as large as the request said it was. It is kept in the repository now (`crates/vendor/tiny_http`), changed so that it reads what is left a few KiB at a time, and closes the connection instead when more than 1 MiB is left.
- An app's events waited, and the relay that reads them dropped its connection and tried again, whenever two transactions that write were open at once past the last one to end.
- A container whose image names a user other than root could hang as its first process changed to that user, on a busy node, and then could not be stopped: it held the container's lock for ever. It now changes user by system calls of its own, and one that does not reach its command in 30 seconds is ended. This is in the agent that runs containers, and takes effect when the agent is started again (see below).

### Upgrading from 0.9.0
- **The agent that runs containers stays the old one** after an upgrade on a Linux node. The new kegd runs once kegd is restarted: `Scripts/install-linux.sh` does that, and after `keg update` it is `sudo systemctl restart kegd`. The containers keep running in the old agent. Until it is started again, `keg ps` and `keg vm status` say so, and services from outside, kept volumes and walled containers are refused. `sudo systemctl kill kegd` starts it again (systemd starts kegd, with a new agent): every running container stops; Keg's services and machines start again, other containers do not. On a Mac, the app updates itself, but the Linux machine goes on running 0.9.0 until it is stopped: Stop Keg and then Start Keg in the app (or `keg vm stop` and `keg vm start`) runs 0.10.0 and its new agent. That stops every running container.
- **Walled containers** (a service from outside, and its build) are on a bridge of their own, `kegw0`, and the node keeps them from itself with rules that match only what comes in on that bridge. Nothing of it is made until the first walled container. Their range is 10.89.0.0/16, unless an address or route of the node's own overlaps it (a Podman network, say): then the first free of 10.90, 10.91 and 10.92.0.0/16, kept from then on in the agent's folder (`walled-range`). A node whose networks cover all four runs everything but walled containers.
- Building a service from its folder is off on every node, upgraded or new: `keg system builds on` turns it on where a person develops services.
- After an upgrade, `keg system ls` says the realtime service "asks for listens:app.bound too: keg system install realtime": it goes on running as before without it, `keg system install realtime` gives it (so that it is told when an app is bound), and it is safe to leave.

### Going back to 0.9.0
- First remove each service from outside with `keg system rm <name> --data`: its container, its volume, its filesystems and what its install brought to the image store go with it. 0.9.0 does not know them, and would leave them.
- Then, with kegd stopped, `sudo sh remove-walls.sh` takes away the walled bridge `kegw0`, its rules (IPv4, IPv6 and nft), the walled range's way out and the note of which range was chosen. The script is a file of the release, and `Scripts/remove-walls.sh` in the source. If kegd's `--root` is not `/var/lib/keg`, give that folder to the script: `sudo sh remove-walls.sh /srv/keg`.
- An app's database keeps the tables and functions its capabilities made (the `keg`, `keg_crypto` and `keg_horizon` schemas); 0.9.0 reads none of them, and they do no harm. The node's own database keeps the new tables beside the old, which 0.9.0 leaves alone.

## [0.7.0] — 2026-09-21

### Added
- **Cooper, the built-in agent** — an on-device agent on Apple's FoundationModels (`SystemLanguageModel.default`): no cloud calls, no account, nothing leaves the machine. Ask "what's running?" or "why did my container fail?", have it pull an image, bring up a Compose stack, or navigate the app ("open the logs view"). The architecture is sized to the on-device model: each turn classifies intent, then runs one specialist session with at most five tools (overview, containers, images, compose, system/k8s); the maintained knowledge base is served on demand via a `keg_docs` tool instead of inflating the context; live state arrives as a compact per-turn snapshot; transcripts trim on overflow with one retry; throttled turns back off exponentially.
- **Cooper permission gate** — Settings → Cooper picks the mode: Explore (look, never touch), Ask (an approval card for every change), Execute (routine actions applied autonomously). Destructive operations — removing containers/images, compose down, stopping the runtime, deleting the cluster — require approval in every mode. The gate suspends inside the tool call and resumes when you answer the card; the 4th identical tool call in a turn is refused with change-your-approach guidance.
- **Cooper conversations persist** on-device at `~/.keg/cooper` and rehydrate on the next launch (stage tracing in `debug.log`). Right-click any container or image → "Ask Cooper About This…" opens the panel with the object preloaded; the toolbar button uses a pure-SwiftUI barrel mark.
- **One instance, one window** — a POSIX pid guard makes a second launch focus the existing app instead of racing it (lowest pid survives); `keg://` deep links always land in the live window, and a stale `/Applications` copy hijacking the scheme is detected.
- **Settings rebuilt into six domain tabs** — Keg, Apple Containers, Docker, Kubernetes, Cooper, About — with host-bounded sliders that save on a debounce, the runtime's per-machine **data location** (app-root) settable through a volume browser with a refuse-to-start preflight, and the container config surface exposed: home mount (ro/rw/none) and builder image as grouped rows.
- **Docker API completions** — `--rm` is honored (AutoRemove), the prune routes work (containers, images, networks, volumes), and `POST /wait` is bounded so a stalled exit delivery falls back instead of hanging `docker run`.
- **Honest lists** — container/image lists carry truth-in-listing subtitles, an All|Running segmented filter with visible counts, and chips that say what they do; volumes can be created from the UI; Compose guards against a stale or missing compose-file path.
- **User guide** — a twelve-page plain-Markdown docs set (`docs/guide/`) covering every app area, linked from the website and in-app help.

### Fixed
- A wedged container runtime is survivable and diagnosable: CLI operations run bounded, the runtime reports `.unresponsive` with backoff instead of hanging the UI, and the Health panel surfaces diagnostics with one-click recovery.
- The Cooper panel's "Open Apple Intelligence Settings" now opens the Siri & Apple Intelligence pane (the old anchor landed on General on macOS 27).

### Known limitations
- Some accepted Docker-API connections never dispatch their first request (the client waits until EOF while an identical fresh connection succeeds) — a `DockerHijackHTTPChannel` pipeline race under investigation; `/wait` itself is bounded, but occasional `docker run` EOFs can still surface.

## [0.6.0] — 2026-09-18

### Added
- **`docker cp`** works end to end — file and directory, in and out, including into-directory semantics — via the `/archive` endpoints (HEAD stat with the base64 `X-Docker-Container-Path-Stat` header, XPC `copyIn`/`copyOut`, tar handling).
- **Restart policies**: `--restart always / unless-stopped / on-failure` persists as a container label; the event bus (now always polling, no `/events` subscriber needed) revives crashed containers with a crash-loop cap; API stop/kill suppresses auto-restart; a startup sweep revives `always` containers daemon-style.
- **Late attach**: API-started containers keep their stdio in a ring-buffered buffer, so `docker attach` on a *running* container replays recent history then streams live. Attach-before-start (`docker run`) uses direct pump wiring. `keg attach [-i]` joins from the companion CLI.
- **Certification suite** (`Scripts/certify-ecosystem.sh`): runs compose stacks and Testcontainers against the socket with tool discovery, and writes the pass matrix to `docs/certification.md`.
- **CI on a real Mac** (`.github/workflows/contract.yml`): the 21-check Docker CLI contract suite on a self-hosted `macos-container-runtime` runner on every push/PR.
- **Homebrew cask** (`Casks/keg.rb`) ready for submission; installs the app and puts `keg` on PATH.

### Fixed
- **The crash class behind months of flakiness — XPC fd double-close**: Apple's `XPCMessage.set(FileHandle)` *closes the descriptor after transfer*. Every stdio fd Keg handed to `createProcess`/`bootstrap` died in-process, and our later closes (or FileHandle deinit) landed on recycled fd numbers — killing CLI pipe reads (NSException) and NIO sockets (EBADF write preconditions) at random. Stdio now transfers dup'ed fds in non-owning FileHandles; our originals close once, at the right time. Verified: 20/20 rapid `docker run` with exact exit codes, 10× exec loop, full contract suite green repeatedly.
- Hijacked-connection writes are serialized on the channel's event loop; error responses to HEAD carry no body (Go client connection poisoning); directory stat mode carries Go's `ModeDir` bit so `docker cp` resolves destinations correctly.

### Known issues
- After heavy kill -9 churn, Apple's runtime vmnet service can wedge machine-wide (`container network create/list` hangs). Fixed by a reboot — a runtime-level issue, tracked for an upstream report if it reproduces.

## [0.5.0] — 2026-09-18

### Added
- **Docker CLI daily-driver parity**: the Docker API socket now backs the full `docker` workflow, verified end-to-end against the real docker CLI (29.x) by `Scripts/docker-cli-contract-test.sh` — all 15 checks green:
  - `docker run` streams stdout/stderr and propagates real exit codes (verified `exit 7` round-trips)
  - `docker exec` works (including `-i` stdin and exit codes) via a from-scratch HTTP connection hijack: Hummingbird has no upgrade support, so Keg runs a custom NIO child channel that answers `101 Switching Protocols` + `Upgrade: tcp` and splices the socket to the container's stdio over XPC
  - `POST /wait` follows the daemon's ≥1.30 contract — headers flush immediately, the JSON body arrives at exit — which the CLI's synchronous ContainerWait handshake requires before it will issue `/start`
  - `docker stats` (XPC-backed CPU/memory/network/pids with pre/post samples for CPU%), `docker events` (poll-differed lifecycle stream that also finally dispatches the webhook manager), `docker volume create/ls/rm`, `docker system df`, `containers prune`, and the classic `POST /build` (tar context, streamed NDJSON output) used by API clients like Testcontainers
  - `docker pull`/`push` stream Docker-format JSON progress mapped from the Apple CLI's plain progress
  - API version negotiation is honest: `HEAD /_ping` (auto-generated) carries `Api-Version`, `OSType`, `Builder-Version`
- **Native advantages made visible**:
  - **Isolation banner** in the container inspector: every container runs in its own microVM with a dedicated kernel — the security property Docker Desktop and OrbStack (shared kernel) can't offer, now stated where operators look.
  - **Memory honesty**: the inspector shows used-vs-limit while running and explains that freed pages stay inside the VM until stop/restart (Apple's runtime doesn't return pages to macOS mid-run) — turning the known limitation into actionable guidance.
  - **x86 images via Rosetta**: the pull sheet picks arm64 (native) or amd64 (Rosetta); `POST /images/create` honors `?platform=`, and create requests carrying `Platform` (e.g. `"linux/amd64"`) pull and run the amd64 variant — verified `uname -m` → `x86_64`.
  - **Real networks**: Docker API network create/delete now provisions actual runtime networks (`container network create` gets its own subnet — verified `keg-net-test → 192.168.65.0/24`), and create requests with a named `HostConfig.NetworkMode` (what compose sends) attach the container to that network via `--network`. In-memory bookkeeping remains only as an error fallback.
- **`keg` companion CLI, installed from the app**: a Foundation-only terminal client for Keg — no docker CLI required. Ships inside Keg.app (`Contents/SharedSupport/bin/keg`) and installs onto PATH with one click from Settings → Keg CLI (or `keg install` itself): first writable of `/usr/local/bin`, `/opt/homebrew/bin`, `~/.keg/bin`, the last with a copyable PATH line. Commands: `status`, `doctor` (pass/fail stack checks with hints), `version`, `env` (DOCKER_HOST exports), `ps [-a]`, `images`, `logs [-f] [-n N]` (stdcopy demuxed, follow until exit), `exec`, `start/stop/restart/rm`, `open [section]` — a `keg://` deep link that focuses the named section in the app (scheme registered in the bundle Info.plist) — and `install`/`uninstall`. Verified round-trip live: install → `keg status` from PATH → uninstall. Built as target `kegcli` (the build dir is case-insensitive; a `keg` artifact would clobber the `Keg` app binary) and symlinked as `keg` on PATH.
- **`keg exec`**: full docker-exec semantics in the companion CLI — the client side of the connection hijack. `keg exec [-i] [-t] [-e K=V]… [-w dir] [-u user] <id> cmd…` streams stdout/stderr live (stdcopy demuxed to the right descriptors), forwards stdin (`-i`, with half-close on EOF), puts the terminal into raw mode for `-t` and sends PTY resizes on window changes, and propagates the command's real exit code. Verified against the running app: multi-frame streams, stderr routing, env/workdir, exit codes, TTY sessions, and clean 404s for unknown containers.
- **Launch at login** (Settings → Docker API) via SMAppService, with socket cleanup on quit — a stale bound socket makes every Docker client hang instead of failing fast.
- New dependencies: NIOHTTPTypesHTTP1 (swift-nio-extras) and ContainerizationOS (containerization 0.42.0, matching apple/container 1.3.1) for the hijack channel and exec resize.

### Fixed
- **Docker API errors now carry proper statuses**: typed Keg errors map to Docker's HTTP semantics (404 for missing containers/images/webhooks, 400 for bad requests) instead of blanket 500s — `keg exec` and the docker CLI both surface real messages now; exec create validates container existence up front.
- **Stale-socket guard hardened**: the launch-time liveness probe before unlinking `~/.keg/docker.sock` now waits 2s instead of 300ms — a slow moment on the owner's side (test hosts, heavy load) can no longer cause a live app's Docker API socket to be unlinked.

### Known limitations
- `docker build` from the docker CLI requires the BuildKit protocol (docker 29 dropped the classic builder client-side); the classic `POST /build` works for API clients. BuildKit session support is future work.
- Attaching to an already-running container (`docker attach`) is unsupported — init-process stdio is fixed at start (same limitation as Apple's own CLI).
