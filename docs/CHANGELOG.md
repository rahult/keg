## [0.12.0] — 2026-11-24

### Added
- **A piece of work's agent reaches its model through Keg's gateway, and is given no key.** With the gateway set up (`keg assistant setup`, `models` running), each round of a work has a door of its own: a socket in the work's `/keg/model`, which only its machine is given, read only, carried to a port of the machine's loopback by a bridge Keg leaves there (`node`), answering OpenAI's Chat Completions (`POST /v1/chat/completions`, streamed or not, tool calls both ways). The runner points Pi at it as a provider of its own (`models.json` in a folder of Keg's making, `openai-completions`), with the round's random token in Pi's environment and no file; the node keeps only the token's sha256 and forgets it, and removes the socket, as the round ends, so another work's token, an earlier round's or none is refused (`401`). What Pi sends is translated into the node's own call (instructions, messages, tools, tool calls and results, carried as data; an image is said to have been there) and answered by the gateway with its own address, organisation and key: an unknown field (`base_url`, `n`, …) is refused, and no header reaches the provider. The work asks the model a person set for works, `keg assistant model --works <model>` (the default until one is set; `ModelSettings.works`), and a request naming another is refused (`400 model_not_allowed`); the project's recipe's provider and model are not used then. Each call is held and settled as `work:<N>` under the work's ceiling ($2 a day) and the node's, at the works' model's price; a call cut off is counted at what the gateway reports in time, else at its worst. A day's ceiling reached answers `429 insufficient_quota` with `x-should-retry: false`, and the round ends with the node's own sentence, which the gate shows; calls a minute or at once answer `429` with `Retry-After`. Bounds: 4 MiB a request, 16 KiB a head, 4 calls of a work at once, and the gateway's own (1 MiB and 5 minutes an answer, 32,000 tokens out). Nothing of what was asked or answered is logged or in an event. The work's evidence, `keg work show` and the console say for each round which model the agent reached this way and what the round spent. The project's `.env` is read only on a node with no gateway set up, as before, and the round says so; a gateway set up and stopped fails the round with a sentence and never falls back. [ASSISTANT.md](ASSISTANT.md) ("Pieces of work reach their model through the gateway").
- **gRPC, and any HTTP/2, through Keg's names.** A service whose `keg.yaml` says `run.protocol: h2c` is reached with HTTP/2 at `<app>.keg.localhost`: with prior knowledge on the names port (as a gRPC client dials) and over HTTPS by ALPN `h2`, so a Go app's gRPC no longer needs `localhost:<port>`. Keg ends the caller's HTTP/2 and checks each request before sending it on: the first chooses the service by `:authority` (over TLS it must be the certificate's name), and a later one for another app on the same connection is answered `421` and sent nowhere, so one connection reaches one app. `CONNECT`, plain or extended, is refused (`405`), as over HTTP/1.1. A service that has not said `h2c`, a container run by hand, the console and Keg's own services are offered and answer HTTP/1.1 only (`505` to HTTP/2), as before. The caller has 30 seconds for its first request, headers are held to 32 KiB, a connection to 100 requests open and the node to 256 such connections, of which one name may have 64, and past 192 only a name with fewer than 8 is let in, so a caller holding many to one app (or a few) leaves room for the rest. [PROTOCOL.md](PROTOCOL.md) ("HTTP/2 and gRPC through the names").
- **The node hands out its Go client as it does `@keg/app`.** `keg app client --go` (the default in a folder with a `go.mod` and no `package.json`) brings a Go app's copy up to the node's, into the folder its `go.mod` replaces `github.com/rahult/keg/sdk/go` with (`third_party/keg` unless it names another folder of the app's, never under `vendor/`), file by file, never through a link; `GET /v1/app-client/go`, a person's, gives it; and a piece of work finds it at `/keg/app-client-go`, with `vendor.sh` to bring `third_party/keg` up to it. Its version is `go-` and the start of a digest of its files.
- **The Go client's audience of roles and users at once.** `tx.Emit(ctx, type, payload, keg.To(keg.Roles("agent"), keg.Users(customer)))` is read by whoever is in either, as `@keg/app`'s `{ to: { roles, users } }` is; `To()` with nothing, the organization beside another, or a kind said twice is refused with `keg.ErrAudience` before anything is sent. The vectors are `@keg/app`'s `test/emit.test.js`.
- **A project names the image its works run in.** `work: { image: "golang@sha256:..." }` in `keg.yaml` is the image of a piece of work's machine, where its agent and its checks run, when the work was not made with `--image`: so a Go project's works can have Go and `protoc`. It is read from the commit the work begins from, so it is what a person merged, never what a work writes for itself, and it must be pinned by its digest (a tag could move after the merge). It runs within the work's walls, as the default `node:22-bookworm` does, and is given nothing more. Keg's own machine for the work, which runs Keg's git on the project, runs Keg's default whatever image the work is made with (`work.image`, `--image` or New work's field, which are for its agent and its checks), so it never runs from an image a person typed or a tag that moves, and an image without git (`alpine:3.20`) makes a work too.
- **`run.health: { grpc: "" }`: a release is ready when gRPC's own health check says so.** Beside an HTTP path and a command, Keg asks `grpc.health.v1.Health/Check` over HTTP/2 without TLS on `run.port`, for the whole server (`""`) or a service by its full name (`notes.v1.Notes`), and takes the release as ready only on `SERVING` with `grpc-status: 0`; anything else, or no answer within 2 seconds, is asked again until the 30 seconds a release has. It needs `run.port`. A Go server answers it with `kegrpc.Health`.
- **A service can be sent an app's past events.** A binding to an app's events that says `from_start = true` asks, in the install question, that "it is sent every event of <app> that is still kept, from the first"; allowed, the relay keeps a place for that binding in each environment and sends it, to it alone, each kept event of its types it was not told of as it came, as far as what had committed when it was bound, at most 500 waiting for it at once (so it never nears the backlog at which it would miss new ones) and within the app's 1200 a minute. `keg system ls` and the console say how far it got. A reinstalled query service no longer starts from nothing when its manifest asks for this. Without it nothing changes: a new binding hears what comes after it is allowed. [PROTOCOL.md](PROTOCOL.md).
- **`keg app remove <app>`.** A person removes an app, typing its name (or `--yes <app>` in a script), or with Remove… on the console's Apps page: it is stopped in every environment here and nothing starts it again, each service bound to its events loses that binding and the token it held, and those services are named. Its database is kept for deploying it again unless `--with-data`, which says first which databases go, with every row in them, and then drops each with its roles and the passwords Keg kept for them. Each step can be taken again, and an environment's record of the app goes only once its data has, so a removal that failed part way (Postgres stopped, say) is finished by running it again; once an app is removed with its data kept, `keg app remove <app> --with-data` finds that data by the app's name and removes it. Refused to agents, services and the assistant. [PROTOCOL.md](PROTOCOL.md).

- **Security: `keg.tenant_ref`, a reference between tenant tables that names only the same organization's rows.** Postgres checks a foreign key without row security, so a plain `REFERENCES suppliers (id)` from one tenant table to another let an organization name another's row, and learn whether an id exists by whether its write was refused. `SELECT keg.tenant_ref('app.orders', 'supplier_id', 'app.suppliers')` (capability file 013) makes the reference `(organization_id, supplier_id)` to the parent's `(organization_id, id)`, with a unique index on the parent's pair if it has none, in place of the column's plain key and doing on delete what it did: another organization's id is refused exactly as a missing one (the same 23503, word for word). The guide and [PROTOCOL.md](PROTOCOL.md) say when it is needed.

- **The console's and the Mac app's New work ask for the machine's image** when the project's `keg.yaml` names none (`work.image`): a Go project's work no longer needs `keg work new --image` from a terminal. Where the project names one, the dialog says which. The node checks the image as it checks `--image`, now before anything of the work is made (`invalid_reference`, where a bad name used to leave a half-made work's folder behind). `POST /v1/work-project-inspect`, a person's, says what a folder's project names.

- **A first round's tests are said against its base.** At a first round's gate there was no earlier count, so a round that added no tests looked like any other ("47 tests as printed"). `keg work show`, the console's work page and the Mac app's now say a first round's count against what the branch it merges into was last checked with, the last round of the latest work merged into it in the same project: "e2e: 47 tests as printed, as on main: no new tests", or "unit: 9 tests as printed (main had 5, as work 12 was checked)". `GET /v1/work/<id>/base-tests`.

- **`keg vm disk --path <folder>`: the Mac's VM disk on another volume.** The data disk lived only in Keg's own folder, and a link made by hand was the only way to put it elsewhere. Now, while the VM is stopped, `keg vm disk --path <folder>` moves it there (a rename on the same volume; on another, only what it holds is copied, hole for hole, and the old file goes once the new one is whole), leaving a link in Keg's folder, which the VM opens through. The disk's folder and any folder containers may write to (shared with `keg vm share` or `--share`, or an agent's workspace) never meet: the disk is not moved into one, below one, or into a folder holding one, and a folder is not shared, or made an agent's workspace, where it is in the disk's folder or holds it (Keg's own folder included); paths are compared through links, whatever their case, and by the device and inode of each folder, so a folder reached by a firmlink (`/System/Volumes/Data/Users/…`) is the folder it leads to. The link in Keg's folder is replaced in one step, made under a name of its own and renamed over the old, so the VM never finds no disk there; the disk is put in its new folder before the old is let go; and `keg vm disk --path` with Keg's own folder moves the disk back there, in the link's place. A running VM is refused. `keg vm disk` says where it is. A link made by hand is taken the same way, and a VM whose linked disk's folder is not there (a volume not connected) no longer starts on a new, empty disk: it says so and stops.

### Changed
- **What a person approves is what is merged.** Approving a work deployed the work's own build even when the branch it merges into had gained commits meanwhile, so `local` and the environment approved into ran code without them, and Keg only said so. Now a work that is behind its base cannot be approved: the gate says how far behind it is and offers **Bring up to date** (`keg work update <N>`, a person's alone), which merges the base into the work's branch in its machine, runs its checks again on the combined code, builds and runs it in `local` and asks again; approving that merges and deploys the build of what was merged. If the work's copy cannot be made again once its branch has moved, the branch goes back to where it was, so the work is still asked about as it was and can be brought up to date again. The files in conflict are said in the console and the Mac app as in the round's note, at most 20 and with any character that would turn the text around written out (the Mac app said "brought up to date" even when the work had gone back to its agent); so are the work's diff, its branch, its base and its evidence, wherever a work's files, branches or summaries are shown. Where the base and the work conflict, the work goes back to its agent for a round, with the files in conflict as the round's note and the merge begun in its directory. In the console's Needs you and work page, and the Mac app's.

### Fixed
- **Security: the node ends a command in a work's machine at its time limit itself.** The limit rested on a `timeout` program inside the machine, which an agent could replace; now the node stops the machine a little past the command's time, whatever is inside it, and the machine starts again when it is next used. A round's door to the model closes with it.
- **On a Mac, short connections to an app are no longer closed without an answer.** At 20–40 callers at once, 1–16% of connections to any app, on `localhost:<port>` and on its name, were closed with nothing sent: the VM's relay listened with socat's queue of 5 not-yet-taken connections, and a virtio socket refuses the sixth at once. It now queues 1024, the VM's helper asks again for up to 3 seconds when the VM refuses (and says in `helper.log` how many it had to), and the Mac's forwarder waits up to 2 seconds for the helper's socket in the same way and says in `forward.log` any connection it could not pass on. Each connection was also held half a second after its answer (socat's linger), so a caller that waits for the close, as `Connection: close` does, waited that long, and an answer slower than half a second to a caller that had half-closed was cut off unsent: the VM's relay is now `keg vm-relay`, which passes each direction to its end, tells the caller at once when the app has finished, and closes the connection 0.5 s later only if the caller has not. 40 callers at once to SupportDesk went from 75 to 400–900 answers a second, none lost. Under sustained load the time each connection took also rose, run after run (41 to 427 ms at 40 callers), and fell only once the load had stopped for a while: every relayed connection asks the node which ports are open, and the node read the whole of `/proc/net/tcp` for each machine to find the ports it listens on, a table that holds every connection that has ended and waits out its TIME_WAIT, about one per request for a minute. With 5,500 of them a single caller's request took 10 ms where it took 3. The node now asks the kernel for listening sockets alone (netlink), whatever has ended. The forwarder and the VM's helper raise their limit of open files from the Mac's 256 to 10,240 as they start (about 60 streams of events or websockets used to reach it), wait and try again when out of open files rather than closing the caller with nothing sent, and the helper no longer spins when it cannot take a connection. Needs the VM image of this release.
- **Keg's own refusals are told as Keg's, with their own kind, in both clients.** `keg.Public` said every refusal raised in SQL as `failed_precondition` "refused", so "no one has signed up with that email" from `keg.add_member` in an app's `Tx` reached the page as "refused". Keg raises its refusals as plain `P0001` text; a refusal is now Keg's own when a function of the `keg` schema raised it (Postgres names it in the error's `where`), and the words Keg's pinned capability files raise give its code and kind: `no_such_email` and `no_such_member` not_found, `administrators_only`, `not_a_member` and `not_open_to_join` permission_denied, `session_not_valid` and `sign_in_failed` unauthenticated, `email_taken` already_exists, a password too short or a role not one invalid_argument, said in Keg's words. `keg.KegRefusal(err)` (Go) and `kegRefusal(error)` (`@keg/app`) give the code; `@keg/app` gains `publicError(error)`, which says what `keg.Public` says. The app's own `RAISE`, even in Keg's words, is still "refused". Both clients are checked against the same vectors (`sdk/go/testdata/public_vectors.json`).
- **The Go client's refusals reach a Connect client's reader.** An error answer says its words in `message`, where Connect reads them; `keg.Refuse` is an app's own refusal in its own words, which `keg.Public`, `WriteError` and `kegrpc.Status` say with its kind and nothing of Postgres's text.
- **A failed job is no longer silent in a Go app.** `WorkOne` gives `*keg.JobFailed` for a job whose handler failed, and `Work` logs each failure.
- **The gate says when a Go test run panicked**, where the short count read as tests removed ("5, was 47"); and the check `keg app new --go` writes runs `go test -v`, since the gate counts Go's tests from the lines it prints only then.
- **A page knows whether it is live.** `@keg/app/browser`'s `subscribe` reports its connection's state, so a page shows "live" only while it is connected.
- **`keg start` and `keg restart` bring back a release that `keg stop` stopped.** Stopping a deployed release's container left it down: start and restart refused it, as nothing a person ran (`startable` was false), until it was deployed again. They now start it again from its release, as a restart of the node does, in a new container; `keg stop` is unchanged.
- **Security: one HTTP/1.1 connection through Keg's names reaches one app.** The name router read the first request's `Host` and then passed the whole connection on, so a later request on a kept-alive connection naming another app (`b.keg.localhost` after `a.keg.localhost`) was delivered to the first app. Every request on a connection is now read, as far as its head and how its body is framed, before it is sent on: one for another name is answered `421 Misdirected Request` after the answers before it, and the connection is closed. Requests two readers could frame differently are refused at the router (`400`) rather than guessed at: `Content-Length` beside `Transfer-Encoding`, `Content-Length` twice or not a plain number, a coding other than `chunked` (`501`), a bare LF or CR, a folded header, a space before a colon, two hosts, an absolute target naming another host, a malformed chunk; `CONNECT` is `405`. An `Upgrade: h2c` is taken out of the request (HTTP/2 is reached with prior knowledge, where each request is checked). Websockets and other upgrades, chunked and streamed answers, `Expect: 100-continue` and pipelining are carried as before. Over HTTPS the connection is held to the name its certificate was asked for: a first request for another is `421`. [PROTOCOL.md](PROTOCOL.md) ("HTTP/1.1 through the names") A connection ends with its caller, also one that goes away while its upgrade is answered (it held a thread of the node and both sockets for ever), and one the node has no thread to spare for is answered `503` while every other is routed as ever.

### Upgrading from 0.11.1
- **The HTTP/1.1 router through Keg's names is stricter.** A request that a service and the router could read two ways is refused at the router where it used to reach the app: `400` for a repeated, comma-joined or `+N` Content-Length, Content-Length beside Transfer-Encoding, Transfer-Encoding on HTTP/1.0, a line ended by a bare CR or LF, a folded header, a space before a colon, two Hosts, HTTP/1.1 without a Host, an absolute-form target naming another host (or with a user in it), and a malformed chunk; `501` for any coding but `chunked`; `405` for CONNECT. A later request on a kept-alive connection for another name is `421` (after the answers before it), as is, over HTTPS, a Host that is not the name the certificate was asked for. `Upgrade: h2c` is taken out of the request. A client that sends any of these, or that sends one connection's requests to two apps, must change.
- **A work behind its base cannot be approved** until it is brought up to date (`keg work update <N>`, or Bring up to date in the console or the Mac app): the base is merged in, its checks run again on the combined code, it is built again and asked about again; a conflict sends it back to its agent. Work waiting at its gate when the node is upgraded is held to this too.
- **Nodes before this release refuse the new fields.** A `keg.yaml` with `work:`, `run.protocol` or `run.health: { grpc: … }`, or a service's manifest with `from_start`, is refused by a 0.11.1 node as a field it does not know. Upgrade every node a project deploys to before committing them.
- **Capability file 013 is given to each app's database at its next deploy, and only adds a function** (`keg.tenant_ref`); nothing changes until an app calls it. Calling it builds a unique index on the parent's `(organization_id, id)` if there is none, without `CONCURRENTLY`, so writes to the parent wait while it is built, and checks the new foreign key over the whole child table. On large tables, call it in a migration of its own, at a quiet time.
- **The Mac's fix for connections closed without an answer needs this release's VM image**: the relay in the VM is `keg vm-relay` from it. The app brings the image with it; Stop Keg and Start Keg once it has updated.
- **What `keg.Public`, `publicError` and `kegrpc.Status` say of Keg's own refusals has changed.** Each is now said in Keg's words with its own kind, where every one was `failed_precondition` "refused": signing in with the wrong password is `unauthenticated` "that email and password do not match", signing up twice `already_exists` "that email is already signed up", adding someone not signed up `not_found` "no one has signed up with that email". `WriteError`'s answer gains a `message` field beside `error`. A page or test that matched "refused" for these must match the new words or kinds; an app's own `RAISE` is still "refused".
- **HTTP/2 through the names is shared and bounded.** It is offered only to a release whose `keg.yaml` says `run.protocol: h2c`; the node holds at most 256 such connections, one name at most 64 of them. A gRPC stream over HTTPS is still cut after 60 seconds with nothing sent either way (a client's keepalive pings keep it) and after 15 minutes in all; one over the plain names port lives at most 15 minutes.

A service's secret is set there in a password field, sent to the node and never shown again; "Stop asking" (and `keg system decline <name>`) stops offering what a person left out, until the service is installed again with different asks.
- **Timers and results on Events.** The console's Events page shows the timers services set and what each finished delivery returned; `GET /v1/deliveries` gives each finished delivery's `result`.
- **An app's binding says which pages are the app's.** `GET /v1/bind/<name>` of an app's events gives `origins`, the exact origins (scheme, name and port) of the pages the node serves for that app's services. A service trusts a page as the app's only by these.
- **A token for an app, and tokens for one organization.** A bind to an app's events with `token = true` in the manifest has the node make a token for that service and app, given to the service with its binding and to the app's servers as `KEG_SERVICE_<NAME>_TOKEN`, with `KEG_SERVICE_<NAME>_URL` (the address a browser opens the service on) and `KEG_APP`, when the app is next deployed; `keg system ls`, the console and the install and removal answers say which apps are yet to be given it. The token reads every organization's content the service holds, so it never goes to a browser: the app's server makes a token for one organization, for at most 15 minutes (`v1.<payload>.<mac>`, [PROTOCOL.md](PROTOCOL.md)), and hands that to its page. It is a bearer token: whoever holds it can use it until it expires, from anywhere, as it is bound to no origin. The query service keeps each organization's events in a database of its own (at most 64 per app, given by recent use: one that wrote nothing for 7 days gives its place up, and one given a place is filled from the app's own database) and answers such a token from it alone, and of them only those for every member: an event the app sent to some users or roles only is read with the app's own token, never through a page, in this version (each relayed app event carries `audience` and `about` from its row, which NATS passes on as they are; an organization given a place is filled with only such events too); it takes the app's own token only from a request no browser made. A bind with no `token` gives the app nothing: NATS's asks for none. A service keeps organizations apart by a relayed app event's `organization`, which, as in 0.10.0, is what the node read from the event's row (`keg.events.organization_id`, which the app's capability layer sets from the actor), never what the app wrote in its payload.
- **`@keg/app` for services and their apps.** `@keg/app/node` gains `hostAllowed(host)`, the check of `Host` both services use; the new `@keg/app/service` gives an app's servers `serviceFor(name)` (its token and address) and `serviceToken(name, { org, ttl })` (a token for one organization).
- **[PROTOCOL.md](PROTOCOL.md)** gains bindings, a service's own events, timers, an app's events and pages.
- **Who is sent an app's events, said one way only.** `keg.expose_events_to(types => ..., roles => ...)` sends them only to those roles, and `keg.hide_events_from(types => ..., roles => ...)` to every member but those; `keg.expose_events(types, roles)`, which took the roles not sent them and was read the other way round, still works. `keg.off(type, job)` takes back a `keg.on`, and says so if there was none.
- **An app reads its own events, each member only those meant for them.** `keg.emit(type, payload, audience)` records who an event is for: `'{"organization": true}'`, `'{"roles": [...]}'` (at most 20, each a plain word) or `'{"users": [...]}'` (at most 100, each a member of the organization). It fails closed: a null audience, or `to: undefined` or `null` in `@keg/app`, is refused, never read as the whole organization; that is said only by leaving the audience out or naming the organization. The view `keg.my_events` (id, type, payload, at, actor, about) gives the member acting their organization's events of an audience they are in, behind a security barrier, read newest first by an index and a page at a time by `(at, id)`. Organization and audience decide who may read an event; `keg.expose_events*` decide only what the realtime gateway pushes, so what is pushed is always among what may be read, and `keg.visible_events` now honours the audience too. A job, as the organization's `system` actor, reads what is for the whole organization and what names `system` among its roles, never what is for users. `keg.emit(type, payload, audience, about)` says what an event is about (`ticket/42`, at most 200 bytes, refused if longer), in a column of its own and never from the payload, so a long `payload.subject` is only a payload; an index makes "events about this, newest first" cheap, and adding the column writes no row again. `@keg/app` has `db.emit(type, payload, { to: { roles } | { users }, about })` and `db.events({ type, about, limit, before })`, which reads each page, the first or one far back, from the index whatever Postgres's statistics say (with sorting turned off for that statement alone), and the node has Postgres look at `keg.events` again once it has built one of its indexes, so the columns 008 adds have statistics. The relay to services from outside is not held to an audience.
- **`keg app jobs`** lists an app's jobs that wait, run or failed, with their attempts, when each runs next and its last error, made safe to print (`--env`, `--failed`, `--json`); `keg app jobs retry APP ID` and `keg app jobs retry APP --failed` put failed jobs back to waiting with their attempts reset. `keg app show` and the console's Apps page say how many are being retried and the last error, and name a job that no worker has taken for five minutes ("is its handler registered?"); the console has a Retry button. Like `keg app show`, these are a person's: an agent is refused them.
- **A check may ask for a database of its own.** In an app's `keg.yaml`, `checks: [{ name: e2e, run: "npm ci && npm test", db: true }]` runs the check against a Postgres of its own: a container started for it from the image the node's shared Postgres runs (pinned, so nothing is fetched; a node that has never run Postgres fetches it by a digest written in Keg, never by its name), with 256 MiB of memory, 1 GiB to write and its newest 10 MiB of output kept, walled so that it makes no connection of its own, at its own address, with no port published. Containers on the node's bridges cannot reach it. Work machines and other containers that share the node's network can reach its address over TCP: only its password, 192 random bits given to that check's command alone, keeps them out. Without it, a hostile piece of work can at worst use up that server's connections or memory and so make another work's check fail, never pass; the node's shared Postgres is open to them in the same way. Not built yet: a unix socket in the work's own mount instead of TCP, or work machines on a bridge of their own with one opening for each check. In it are the app's capabilities and the work's own migrations, at the commit checked, and the check is given `DATABASE_URL` (with `KEG_ENV=check`, `KEG_SERVICE` and `PORT`; no secrets, no data and no realtime of any environment). It is ready in about a second, and says so in the check's output. A migration that fails fails the check, with Postgres's words. The container is removed when the check ends, and what a node that stopped meanwhile left is removed when it starts. At most two run at once; a third waits up to ten minutes, and is then given back to be run again, never failed for waiting; those that wait have their turns in the order they came. One that runs out of memory or is not ready in 90 s is started again, three times in all. A node that cannot run one at all (no loop devices, an agent from before, which kegd asks to be restarted, or an image it cannot fetch or that is not the one pinned), or one that did not start three times, gives the check the new verdict `error`, with why, which holds the work at the gate rather than trying again. The evidence says "with a database of its own".
- **A tenant table says what each command allows.** `keg.tenant_table('app.ratings', update => false, delete => false)` (and `insert => false`) turns those commands off for every role the app connects as, its jobs among them: an UPDATE or DELETE touches no row, an INSERT is refused. Called again it keeps what it is not told: a command turned off stays off until a later call turns it back on by name (`update => true`). Called with the table alone the first time it is as before: every member of the organization may read and write every row unless a restrictive policy says otherwise. The guide and `keg app new`'s migration say so, and that a restrictive policy `FOR ALL` covers `SELECT` too.
- **The gate shows how many tests each check ran, against the round before.** The checks service reads the counts that node --test, cargo test, pytest, jest, vitest and go test -v print, as well as JUnit and TAP, into its record ("e2e: 41 passed, 0 failed"); what it reads never decides whether a check passed, and a number past ten million, or a sum past it, is no count: it is shown as unknown, and nothing a check prints can make the checks or `keg` overflow. The count is kept with the record as numbers (`tests` in its evidence), never read back out of a summary a check's name could fake, and is shown "as printed". `keg work show` and the console's work page say "e2e: 41 tests (was 41)", as numbers only, so that tests asked for in a note and not added show at a glance.
- **Cleaning up, and what building keeps.** `keg cleanup` shows what is on the node's disk by kind, with sizes (layers images share counted once), and item by item what a cleanup would remove and why each thing is kept or not; `keg cleanup --apply` removes it and says what it freed. What is always safe goes: the images of builds older than the newest 5 of each service, checks' containers that have ended, and layers and blobs nothing refers to. Only when asked: `--works` (the machines and folders of finished pieces of work whose days are up), `--images` (images nothing uses, pulled or built by a person), `--containers` (containers a person ran that have ended), `--build-cache`, and `--volumes NAME…`, each volume by its name. `keg rmi --damaged FILE` removes an image record that cannot be read, as `keg cleanup` names it. `--dry-run` is what it does without `--apply`; `--json` gives it whole. Nothing that runs, that a change waiting for approval would deploy, that a rollback goes back to, that a piece of work at its gate asked about, that a machine or a service from outside is of, or that is the shared database's image is ever removed. Only a person may: an agent is refused all of it, and a service with it. `keg system keep builds N` and `keg system keep work-days N` (0: as soon as it is finished) say how much is kept, and `keg system keep works ask|auto` whether Keg asks before clearing finished work (`ask`, the default) or the node clears it by itself. The console and the Mac app have a Storage page, with the disk by kind, these settings, and Clean up, which shows exactly what goes and what it frees before anything does.
- **The node cleans up after itself.** After each build and once a day it removes what is always safe to remove, from a day after it first looks: until then it only says what it would remove (`keg cleanup` shows when it begins). Keg asks before clearing finished work: a finished piece of work (merged, or turned down at its gate) is shown as one that can be cleared 7 days after the node saw it finish, and its machines and folder go only when a person ticks it (or turns `keg system keep works auto` on). Its branch, evidence, notes and what it changed stay, and once it is cleared it cannot be taken up again. Its folder is removed only where it was made, never through a link, and not while any container has it. A layer made in the last hour is never taken, so nothing a pull, a build or an image sent from another node is still using goes. On a Mac the node then tells its disk which blocks are free, at most once a day, so the space comes back to the Mac; elsewhere only with `keg cleanup --apply --trim`.
- **A disk nearly full is said.** From 85% full the console's first page, `keg system ls` and `keg vm status` say so and how to free space; at 95% a build or a `keg pull` is refused before it writes anything, with how to free space, rather than failing part way. `keg vm status` shows how much the disk image takes on the Mac beside what the node uses of it.
- **A cleanup knows what works were handed and what their checks ran against.** Storage counts the files handed to pieces of work as a kind of its own ("Files handed to works"); they go when their work is cleared, once nothing has them, and never before, and a finished work's item counts them. A check's own instance of a service and its volume are kept while the check has them; one that has ended and that its check no longer has goes with the checks' throwaway containers.

### Changed
- **The Mac's Linux machine is smaller and starts sooner.** Its image is made of only what the machine runs, from a root of its own, where it was the whole container Keg is built in, with its C compiler, binutils, make, Perl and rsync: 17 MB to download where it was 62, and 50 MB in the VM's memory where it was 189. On an Apple M4, six boots of each: the API answers 0.8 s after `keg vm start` (median; 1.4 s before), and the VM uses about 160 MB where it used about 300. It ships 36 Alpine packages where it shipped 71, and 13 sources under the GPL or LGPL where it shipped 29 (3 of them under version 3, where it was 11: no cpio, make, rsync, gmp, mpfr, mpc, libidn2 or libunistring); the GPL source a release carries for them is 43 MiB where it was 225. A throwaway node ran on it every path that runs a program of the image: a published port, a container as another user, `keg build`, Compose with a named volume, Keg's own services, a service from outside built behind walls on spaces of a fixed size, shared folders, an app on the shared Postgres, a piece of work's machines, Rosetta, the SSH agent, Docker's API, and a stop and start with its data kept. The release checks the image holds no compiler or build tool and stays under 20 MiB packed, 56 MiB unpacked.
- **On an agent's credential, `keg machine shell NAME -- <command>` and `keg sandbox` work.** They opened a session, which an agent may not; they now run the command to its end through the calls an agent has (as `keg_machine_run` and `keg_sandbox` do), with its output and exit status. An agent's machine shell runs one command at a time; its sandbox has nothing of the computer in it. `keg machine create` on an agent's credential asks the Mac to share nothing, as `keg_machine_create` does: the folder must be one the node gives to agents.
- **Faster where the node is asked most**. On a Linux node with 200 containers: `keg ps` takes 3.8-10.4 ms where it took 14.7, `GET /v1/containers` 2.1-3.7 ms where it took 12.9 (846 a second from 8 clients, where it was 296), Docker's `containers/json` 6.9 ms where it took 15.3, and a refresh of the Mac app costs the node 12-20 ms of processor where it cost 66 (the console's, 10-14 where it was 45). kegd keeps its connections to the runtime agent, so a question of it takes 9-19 µs where it took 70-120. Claiming a delivery with 2-3 thousand waiting and 9 thousand done takes 0.30 ms where it took 26.4, and finding when the next is due 0.13 ms where it took 18.2. The Mac's forwarder asks the node for its ports once and is answered when they change, where it asked ten times a second: about 20 ms of the node's processor each 30 seconds where it was 230-310. `keg logs -f c | head` ends once `head` has its lines.
- **A walled container is reached by the node from an address of its own** on the walled bridge, the last of the walled range (`10.89.255.254` unless the range moved), which is never handed to a container. A walled container's own rules let its published and reached ports in from that address alone, so they keep containers on the node's bridge out even while the node's own rules are being made again, and they are made before its link is up. A service from outside sees the node's connections come from that address.
- **The console refuses a request another site's page sends**, by its `Origin`, whatever it carries; a request with no `Origin`, as `curl` and `keg` make, is answered as before.
- **The Keg License.** Keg is closed source and free to use under the Keg License (`LICENSE.md`, `keg license`), which comes with the app, the `keg` command, the disk image and each release; `keg license --third-party` lists the software by others in Keg. It was in 0.10.0's files and is said here.
- **A new container may no longer be named `machine-work-…`**, through `keg run --name` or the Docker API: those are the names of the machines Keg makes for pieces of work. A container that already has such a name is left as it is.
- **A relayed app event carries the organization the node read from its row** (`organization`, from `keg.events.organization_id`, which the app's capability layer sets from the actor), never what the app wrote in its payload, so a service may keep each organization's events apart by it.
- **The Mac app no longer asks the node for everything every 2 seconds.** It holds the node's log of events open, as the console does, and asks again only for what an event concerns, and only where it is seen: the section shown and the sidebar's counts, or with no window only what the menu bar's item shows. Charts are read every 2 seconds only while they are in front; everything seen is asked again every 30 seconds only while the window is in front; a node that does not answer is asked a second later, then twice as long each time up to half a minute. While the node is at rest the log is not held open, since a held request counts as work and its VM sleeps only with no connection open: it is looked at every 15 seconds and let go at once, and while the VM sleeps nothing is asked at all. Storage's report, which the node walks its disk to make, is asked for only while Storage is shown: when it opens (at most once a minute), after a cleanup or a change to what is kept, and when the log says something that held space went, at most every 15 seconds.
- **An app's events reach a service in the order they were read**, for each app and environment: a later one is not claimed while an earlier one waits, runs or backs off, and one failed for good holds nothing back. A service is still told of an event again after a hold runs out, so it is still safe to be told of each twice.
- **What a service held is waiting again at once when a person ends its run** (stopped, removed, installed again) or the node starts again, its try not counted, and a claim that was waiting as it stopped is given nothing. Before, each waited out its hold of 60 seconds, and an app's next event could go ahead of it. When its run ends by itself (it exits or crashes) holding a delivery, the try counts, so an event it dies on every time fails after its fifth try and the app's next events go on. `keg events skip <delivery>` (and "Skip" on the console's Events page) lets a person fail a waiting one sooner. How far behind a subscriber may be on an app's events is counted for each environment, so `local` cannot starve `prod`.
- **A name in `local` that is an app's service is that service's, and never a person's container of the same name**: while the service has no port, the name leads nowhere.
- **The install question says what is true** of a service bound to an app's events: that it holds every organization's content of what it hears, who may read it, what a token for the app is for and when it is given, and that a published port is reached by any program on this computer.

### Fixed
- **Two nodes on one Mac no longer hand out each other's addresses.** Each node's VM serves names on 7380 and 7443, and the Mac's forwarder only logged when one was taken there, so the second node's `KEG_REALTIME_URL`, its apps' origins, its console link and its "Try it" and "Open" links led to the first node, with what they carried (a signed-in user's session token, the console's link). Now a port of Keg's own that another program holds on the Mac is opened on the next free one (kept in `~/.keg/runtime/mac-ports.json`, so links stay the same), the forwarder tells the node what leads to it (`PUT /v1/reach`, a person's alone), and the node hands out only that, and nothing before it is told. `keg vm status` says which ports the node got and why. A port asked for by number is never moved: `keg ps`, `keg ports` and the console say when the Mac does not reach it. An app keeps an address it was given until it is next deployed, which `keg app show` and the console say. See "Where a node is reached" in [PROTOCOL.md](PROTOCOL.md).
- The Mac app no longer ticks, for a person installing a service from outside again, what reaches past its socket (a port of this computer, the internet), as the command line and the console do not. It did in 0.10.0.
- **Each environment of a service keeps its own way in.** A release approved into `staging` no longer takes `localhost:3000` from the same service in `local`, after which every deploy to `local` failed until staging was stopped by hand. The first environment of a service to be deployed has the port its `keg.yaml` names; another environment of the same service is given the next free port, keeps it, and is reached by its name (`web.staging.keg.localhost`) as before. `keg services` shows each one's port, and on a node where another environment already holds the port `local` names, says which and the commands that give `local` its port back (an upgrade does not move it). Another service that names a port already held is still refused.
- **`GET /v1/apps/<app>` no longer fails while the app is first deployed.** The app is bound before its database, roles and grants are made; a reader meanwhile (the console asks every few seconds) was answered 500, and could make the app's password itself, beside the deploy. An environment whose database is not made yet is shown without jobs, and nothing is made by reading. Also: `keg ps` says how many app containers it left out and that `keg ps --apps` shows them; `keg services` says what runs in the other environments; `keg events` says its times are UTC; the build agent is told to install the project's dependencies and run its checks before it commits, and never to commit with a test it knows fails.

### Upgrading from 0.10.0
- **Restart the runtime agent on a Linux node.** The agent that runs containers now speaks protocol 4, where 0.10.0's spoke 2. A node upgraded without restarting it goes on with the old one: containers keep running and most things work, but a cleanup, a check with a database, a check with services, and reaching a walled container are refused, each with a message that names the restart. `sudo systemctl kill kegd` restarts it (systemd starts kegd again, with a new agent): every running container stops; Keg's services and machines start again, other containers do not. On a Mac, Stop Keg and then Start Keg in the app (or `keg vm stop` and `keg vm start`); that too stops every running container.
- **The node removes nothing by itself for a day after its first start on this version**, and only says what it would remove; then, after each build and once a day, it removes the images of each service's builds beyond the newest 5 that nothing needs, and what is otherwise always safe to remove. To keep more builds, say so before then: `keg system keep builds 20`. `keg cleanup` shows what would go and the day it begins. Releases stay in the record; a release whose image has gone can no longer be promoted or deployed again, but what runs and what a rollback goes back to are always kept.
- **Clearing finished work is off.** The node never clears a finished piece of work by itself unless a person turns it on (`keg system keep works auto`); until then it lists it as work that can be cleared, and a person ticks it.
- **A work's machine that was running across the upgrade has no record of the container Keg made for it** until it is started again: Keg now finds a work's machines by that id, never by a name. Until then, clearing that work leaves its folder and says why ("Keg has no record of the container it made for …"); stopping and starting the machine, or the node, records it.
- **Turn the assistant on, if wanted.** Nothing of it runs after an upgrade: `keg assistant setup --env-file <path to a .env>` reads `OPENAI_API_KEY` once, seals it for the model gateway, and installs and starts the gateway and the assistant. Its spend is held to $5 a day for the assistant and $20 for the node unless changed with `keg assistant limits`. What it reads is sent to OpenAI, log lines among it; anyone with the console's link can read its conversations and confirm the changes it proposes, so treat that link as the node's key.
- **The node's own store gains, as it starts:** new columns of deliveries, evidence, finished work and backing services (a backing service from before is a person's); the tables `confirmations`, `runs`, `run_steps`, `conversations`, `secret_marks` and the model ledger's; and the table of bindings is made again, in one step, to take the kinds `model`, `tools` and `runs`. An app that uses events or jobs is given capability files 007 to 009 at its next deploy, or sooner, when the relay next reads its events (008 adds two columns to `keg.events` without writing a row again; the node builds its two indexes afterwards, concurrently, and `keg app show` says while it does).
- Where a Mac's port of Keg's own (7380, 7443 and the rest) is held by another program, the node is now reached on the next free one, kept in `~/.keg/runtime/mac-ports.json`; an app keeps an address it was given until it is next deployed.

### Going back to 0.10.0
- **Not supported once the assistant or the model gateway has been set up.** 0.10.0 does not know Keg's services `models` and `assistant`, nor bindings of the kinds `model`, `tools` and `runs`, which it answers as bindings that are not there.
- Otherwise: 0.10.0 leaves the new tables and columns of the node's store as they are, and does not read them: conversations, runs, proposals and the model ledger stay, unread, until this version is installed again. ## [0.10.0] — 2026-11-22

### Added
- **Work and gates.** `keg work new` begins a piece of work in a project, on a branch and in a worktree of its own; agents take it through build, test and ship in a machine of their own, and each stage keeps what it found as evidence. A gate waits for a person: `keg needs` lists what waits, `keg gate approve|reject` answers, and `keg work send-back` sends it back with what is to be changed. Nothing is merged until a person approves. An agent sees none of this and answers no gate.
- **A log of events.** Every change the node makes (work, stages, gates, evidence, change sets, services, apps, containers) is written as an event in the same transaction as the change. `keg events` reads it; `keg events failed`, `keg events retry` and `keg events timers` show what Keg's services have yet to do. The console and the Mac app have an Events page, and refresh when something happens.
- **App capabilities.** A `keg.yaml` with `app:` and `uses: [data, identity, events, jobs, realtime]` gives an app a database of its own in each environment, in which tenancy is the database's to keep: sign-in, sessions, organizations and members; events and jobs, at least once; and a realtime gateway that sends each subscriber what its user may read. `keg dev` runs one, `keg app ls|show|new|stop|org` looks after them, and `@keg/app` is the library.
- **Keg services.** Keg runs services of its own on the node, each in a container with a socket and grants of its own: the console, the checks that the test stage asks for, and the realtime gateway. `keg system ls`, `install`, `start`, `stop` and `rm` look after them.
- **Services from outside.** A folder with a `keg.service.toml` is installed with `keg system install <folder>`: a person is asked about each thing it asks for, in plain words, and it holds only what was allowed. It runs pinned by digest, behind walls: no capability, no network but its socket (or the public internet only, if that was asked and allowed), memory, processes and disk capped, a volume, secrets and ports only through bindings of its own, at most 16 connections and 8 requests at once. It can be told of events, write its own, set timers and hear an app's events. Building one from its folder on the node is off until a person turns it on with `keg system builds on`; off, a service names its image by digest (`image = "…@sha256:…"`). A node needs loop devices and `mkfs.ext4` (e2fsprogs) to run them; one without says so and refuses them alone. [PROTOCOL.md](PROTOCOL.md) is what such a service may rely on.
- **The console has two modes**, Containers and Builder, with a guide through both in ten steps; `keg example hello-keg` makes a small project to try them with.
- **The Mac app** has the same two modes and guide, and new sections: Needs you (pinned, with its count), Work with Approve, Send back and Reject at a gate, Keg services with the question of what each asks, Apps, and Events.
- **The source of the GPL and LGPL software in Keg**, the kernel and the Alpine packages of the Linux machine, is published with each release, as `keg-<version>-gpl-source-kernel.tar.xz` and `keg-<version>-gpl-source-packages.tar`.

### Changed
- What a request names as a number (a CPU limit, a timeout, a duration, a recipe's minutes) is refused or held at its most when it is too large to hold, never a panic; a release build checks every sum for overflow.
- A panic while the control database is held fails that request alone: the node goes on.
- **An app's own transactions left idle are ended.** The roles an app connects to its database as have `idle_in_transaction_session_timeout` set to 10 minutes: a connection left idle inside a transaction for that long is ended by Postgres, and its transaction rolled back. One left open would hold back that app's events.
- **A Dockerfile or `.dockerignore` larger than 1 MiB is refused**, before more of it is read, by every build: a service's, and a person's own `keg build`, `keg up` and `docker build` alike.
- **What a request sends is held to a size.** A request to the Keg API, the console or the Docker API whose body is JSON is read to 1 MiB (evidence, whose body is kept to 1 MiB and cut past that, to 8 MiB). A blob or a volume's contents sent to the node is written to disk as it arrives, up to 64 GiB; a build context or an archive sent into a container through the Docker API, up to 16 GiB. A request past its limit, whether it says so or turns out so, is answered 413 with a sentence that says the limit, and its connection is closed as soon as that answer is sent, so nothing more it sent is read, as a body or as a request.

### Fixed
- One request could make kegd, or `keg ui` and `keg files mount`, end: the HTTP library they use read what was left of a body it did not need into one buffer as large as the request said it was. It is changed so that it reads what is left a few KiB at a time, and closes the connection instead when more than 1 MiB is left.
- An app's events waited, and the relay that reads them dropped its connection and tried again, whenever two transactions that write were open at once past the last one to end.
- A container whose image names a user other than root could hang as its first process changed to that user, on a busy node, and then could not be stopped: it held the container's lock for ever. It now changes user by system calls of its own, and one that does not reach its command in 30 seconds is ended. This is in the agent that runs containers, and takes effect when the agent is started again (see below).

### Upgrading from 0.9.0
- **The agent that runs containers stays the old one** after an upgrade on a Linux node. The new kegd runs once kegd is restarted: after `keg update`, that is `sudo systemctl restart kegd`. The containers keep running in the old agent. Until it is started again, `keg ps` and `keg vm status` say so, and services from outside, kept volumes and walled containers are refused. `sudo systemctl kill kegd` starts it again (systemd starts kegd, with a new agent): every running container stops; Keg's services and machines start again, other containers do not. On a Mac, the app updates itself, but the Linux machine goes on running 0.9.0 until it is stopped: Stop Keg and then Start Keg in the app (or `keg vm stop` and `keg vm start`) runs 0.10.0 and its new agent. That stops every running container.
- **Walled containers** (a service from outside, and its build) are on a bridge of their own, `kegw0`, and the node keeps them from itself with rules that match only what comes in on that bridge. Nothing of it is made until the first walled container. Their range is 10.89.0.0/16, unless an address or route of the node's own overlaps it (a Podman network, say): then the first free of 10.90, 10.91 and 10.92.0.0/16, kept from then on in the agent's folder (`walled-range`). A node whose networks cover all four runs everything but walled containers.
- Building a service from its folder is off on every node, upgraded or new: `keg system builds on` turns it on where a person develops services.
- After an upgrade, `keg system ls` says the realtime service "asks for listens:app.bound too: keg system install realtime": it goes on running as before without it, `keg system install realtime` gives it (so that it is told when an app is bound), and it is safe to leave.

### Going back to 0.9.0
- First remove each service from outside with `keg system rm <name> --data`: its container, its volume, its filesystems and what its install brought to the image store go with it. 0.9.0 does not know them, and would leave them.
- Then, with kegd stopped, `sudo sh remove-walls.sh` takes away the walled bridge `kegw0`, its rules (IPv4, IPv6 and nft), the walled range's way out and the note of which range was chosen. The script is a file of the release. If kegd's `--root` is not `/var/lib/keg`, give that folder to the script: `sudo sh remove-walls.sh /srv/keg`.
- An app's database keeps the tables and functions its capabilities made (the `keg`, `keg_crypto` and `keg_horizon` schemas); 0.9.0 reads none of them, and they do no harm. The node's own database keeps the new tables beside the old, which 0.9.0 leaves alone.

## [0.9.0] — 2026-11-20

Keg is rewritten. The app that wrapped Apple's `container` tool is gone, and with it what was unreleased in it (managed agents, traces, Cooper, the app catalogue). In its place:

### Added
- **A runtime of Keg's own, in Rust.** It pulls, builds and runs OCI images itself, on Linux directly and on a Mac in a small Linux machine that boots in about a second and sleeps when idle. There is no Docker and no Apple `container` tool underneath.
- **The `keg` command**: containers, images, volumes, Compose files, machines (a Linux system to work in), a sandbox for trying code, `keg init` for setting a project up, `keg k8s` (one node of k3s), `keg migrate` from Docker Desktop, OrbStack or Colima, `keg files mount`, `keg update`.
- **Docker's API**, on a socket of its own: `docker`, `docker compose`, `docker build` with BuildKit on, `docker cp`, `docker push`, restart policies, UDP ports.
- **Services that move.** A `keg.yaml`, environments, releases and change sets with checks and approval, promotion of the exact image between nodes over mutual TLS, rollback, deploys with no gap, a shared Postgres, secrets.
- **Names and HTTPS.** `NAME.keg.localhost` for anything with a port; sharing through a server you run, with a Let's Encrypt certificate for each name.
- **For agents.** `keg agents`, `keg mcp`, and `keg agents --connect claude|codex|pi`; an agent's rights are held by the daemon.
- **A new Mac app**, in SwiftUI: changes to approve, services with rollback, containers with output, files, usage and a terminal, machines, images with a vulnerability check and a search of Docker Hub, volumes, environments and nodes, a menu bar item, settings for the Linux machine. It has the `keg` command and the Linux machine inside it, links the command onto the PATH, and follows the Mac's language, in fifteen.
- **The app, section by section.** An overview; containers that are filtered, searched, sorted, started again, restarted and removed several at a time, each with live charts, how it was made, output with a search and a level filter, files saved to Downloads and a command run in it; images with sizes, how each was built and the progress of a download; volumes made from the app; Kubernetes with its pods and services; sharing; a menu bar that lists what is running; a notification when a change starts to wait for approval; settings that point `docker` at Keg and import from another engine; and `keg://` links.
- **The web console, rebuilt** to the same breadth, with a command palette, keyboard shortcuts and a layout for any width.
- `keg start`, `keg restart`, `keg pause` and `keg resume`; `keg images` says each image's size.
- **Compose projects, builds and networks** in the app and the console: a project is started and stopped as one and its file changed and run again; each build is kept with what it said; networks are listed and removed.
- **A terminal in the app's window**, in a container's pane; a container's ports and variables changed from there; light or dark; a report to copy when something is wrong.
- **Twenty-three more languages** in the app: thirty-eight in all.
- `keg env rm` forgets an environment that has nothing in it, as do the app and the console. Its change sets stay on record.
- One service of a Compose project is started again and restarted by itself, and is still that service of the project.
- A build that fails is kept with the steps it got through.
- **Disk and network, charted** for each container beside processor and memory, and its own address told, in the app and the console.
- **Go to… (⌘K)** in the app: type part of a section's, container's, service's or image's name and go there.
- **The app's language, accent colour, lettering and text size chosen in its settings**, where they are not to be the Mac's. The size is followed by the sidebar, the lists, output and the terminal; small labels keep theirs.
- In the app: back and forward between sections (⌘[ and ⌘]), start, stop, restart and remove on each container's row, and each image marked by its letter and colour.
- **A running container's ports are changed without stopping it**, from the app and the console, where ports are all that change and it already has one open: it is the same container, with everything it has written.
- **A proxy for fetching images**: `keg vm start --proxy http://HOST:PORT`, or the app's Linux Machine settings. One that listens on the Mac itself is reached from the Linux machine too. On a Linux node, `KEG_PROXY` or `HTTPS_PROXY` in kegd's environment does the same. A password in the address is kept from containers and from other programs on the Mac.
- **The console, laid out as the Mac app is**: the same sidebar and sections, a toolbar with back and forward, the container list with the chosen container's charts, output, files and terminal below it, and Kubernetes pods and services.
- **The console as a service of the node.** `keg ui` now has Keg run its own console in a container (`keg-console`), made from the keg command itself with nothing fetched, and opens it at `console.keg.localhost` with a link that is the person's alone. It stays up until `keg ui --stop`. `keg ui --local` serves it from the command as before, as does a node that cannot run it.

### Changed
- **Requires macOS 15 or later** on Apple silicon (0.8 required macOS 26).
- The app updates itself as before, through the same feed; an installed 0.8 is offered 0.9. Containers, images and settings of 0.8 are not carried over: they belonged to Apple's `container` tool, which 0.9 does not use.

### Fixed
- A node with a public name did not answer at that name itself, only at the names under it, so whatever else held the port answered with a certificate of its own and browsers warned. The node now has a certificate for its own name and says there what it is.
- A certificate that could not be got for a share was not asked for again for six hours. It is now asked for after two minutes, then ten, then thirty.
- Asked plainly over HTTP, a node sent the visitor on to HTTPS at whatever host the request named. It now does so only for its own names.
- Two kegd on one machine that started their first containers at the same moment could both try to make the bridge, and one container failed with "File exists".
- `keg pause` returned before the kernel had stopped every process of the container.
- On a Mac, a build run within a second of a file being replaced (as an editor saves one) failed with "No such file or directory": the folder shared with the Linux machine went on naming the file that had been there. The build now waits that out.
- After Keg was restarted, sharing the same thing again through a node was refused: the node still held the name for the daemon that had gone. A share whose node has gone now gives its name up at once.

### Removed
- The 0.8 app and everything particular to it: Cooper, managed agents and traces, the app catalogue, Dev Containers, the health score, the embedded terminal, the `keg://` links and its own command-line client.
