02

From first container to production.

Containers, images, volumes, Compose and Docker's API for the work on your computer. Environments, change sets and approvals for moving it to a server. The same app and the same command for both.

No. 01Speed

Containers in Milliseconds

A container runs to its end in about 5 ms through the keg command. From nothing, booting the Linux machine and running the first container takes under a second.

No. 02Idle

Asleep When Idle

With nothing running for a minute the Linux machine is paused and uses no processor. A command, or a connection to one of its ports, wakes it in about 45 ms.

No. 03Compat

Docker's API

Keg answers Docker's API on a socket of its own. Run keg docker use and docker, docker compose, editors and test libraries talk to Keg as they are. There is no Docker underneath.

No. 04Stacks

Compose Files, As Written

keg compose up or docker compose up: health checks, depends_on, service names, volumes and builds, from the file you already have.

No. 05Names

Names, Not Ports

Anything with a port opens by name: web.keg.localhost for a container called web. Over HTTPS too, from a certificate authority that can vouch only for those names.

No. 06Machines

Linux Machines

A Linux system to work in, kept until you remove it. What you install stays, your folders are in it at the same paths, and what you start in it is on localhost.

No. 07Releases

Services That Move

A keg.yaml describes a service once. Keg builds it, releases it, and promotes the exact image from your computer to a server you run. It never rebuilds on the way.

No. 08Approval

Changes You Approve

Every deploy is a change set: what would change, and the checks it passed. Environments that ask for a person wait for one, in the app, the browser or with keg approve, and the app notifies you when one starts to wait.

No. 09Deploys

Deploys With No Gap

A new release starts beside the old one, must pass its health check, and only then takes the traffic. One that fails never takes the port, and the old one carries on.

No. 10Sharing

Share Through Your Own Server

keg share web --via server opens what runs on your Mac at an HTTPS name on a server you run, with a Let's Encrypt certificate. No service in between.

No. 11Security

Vulnerability Check

Check an image's Alpine, Debian or Ubuntu packages against the open vulnerability database, from the app or with keg scan. Only package names and versions are sent.

No. 12Cluster

Kubernetes

keg k8s start, or a button in the app, runs one node of k3s with its state in a volume, ready in seconds once the image is here. The app lists its pods and services.

No. 13Moving in

Bring Your Images

keg migrate brings images and named volumes over from Docker Desktop, OrbStack or Colima. Nothing there is changed.

No. 14App

One App, Nothing Else to Install

The Mac app carries the keg command and the Linux machine inside it and updates itself. Its accent, lettering, text size and language are yours to set, in thirty-eight languages. On any machine, keg ui is the same in a browser.

No. 15Finding

Go Anywhere by Name

Command-K, a few letters, Return: a section, a container, a service or an image, in either mode. Back and forward take you where you were.

No. 16Free

Free to Use

Download it and run it. No account and no telemetry. There will always be a free version.

03

Work that waits for you.

Give a piece of work a brief. Agents take it through build, test and ship, on a branch and in a machine of its own, and each stage keeps what it found. Then it stops at a gate. Nothing is merged until a person approves, and an agent cannot answer a gate.

01

A brief, on a branch of its own

In a project that is a git repository. The work gets a branch, a worktree and a machine; your own folder is left as it is.

keg work new \ --title "Add a version route"
02

Built, tested, deployed, with evidence

Each stage keeps what it found: what was built, which tests passed, which release runs where. The diff is there to read.

keg work show 3 build pass test pass 27 passed ship pass runs in local
03

A person decides

Approve, and it is merged and deployed. Send it back with what is to change, and it is built again and asks again. Or reject it.

keg needs keg gate approve 3 keg work send-back 3 --note "…"
nothing ships until you say
4 records · diff against main
04

Three places for an agent to work.

An agent of your own (Claude Code, Codex, Pi) asks Keg for what the task needs. Each is a Linux container, so what it installs, breaks or leaves running is in there and not on your computer. keg agents prints the guide an agent reads; keg agents --connect claude, codex or pi connects one.

01

A sandbox, gone when the command ends

For trying something: does this library import, what does this script print. The folder it runs in is there to read and cannot be changed.

keg sandbox python -- \ python -c "print(6 * 7)" 42
02

A machine, kept until it is removed

For working on a project. Its folder is in the machine at the same path and can be written to; what is installed stays; a server started in it answers on localhost.

keg machine create app --image node:22 keg machine shell app -- npm test passing
03

A service, released and kept running

For an app that is to run. Keg builds it and numbers the release. Where changes do not apply by themselves, the release is a proposal that waits for a person.

keg up keg promote checkout \ --from local --to staging waiting for a person
AllowedAgent

What an Agent Can Do

  • Run code in a sandbox, and make, use and remove machines of its own.
  • Build images, and propose a release or a rollback.
  • Read what is running, the environments, and the changes and how they ended.
  • Start the databases and queues the app needs beside it.
NeverDaemon

What It Cannot, Whatever It Is Told

  • Approve a change or answer a gate. That is a person's, in the app, a browser or the terminal.
  • Reach folders you did not name: machines are held to the workspaces given to agents.
  • Read an environment's secrets or the node's keys.
  • Go round the limits. The daemon keeps them, not the agent's own client.
05

What the node gives what you build.

A log of everything that happened, a database for each app with sign-in and events in it, and services that Keg runs beside your own, each with only what a person allowed it.

No. 01Events

A Log of Events

Every change the node makes (work, gates, evidence, change sets, services, apps, containers) is written as an event in the same transaction as the change. keg events reads it, and the app and the console have an Events page that refreshes when something happens.

No. 02Apps

Apps With Their Own Database

A keg.yaml with uses: [data, identity, events, jobs, realtime] gives an app a database of its own in each environment: sign-in, sessions, organizations and members, events and jobs delivered at least once, and a realtime gateway that sends each user only what they may read. keg dev runs one.

No. 03Keg services

Services of Keg's Own

The console, the checks that the test stage asks for, and the realtime gateway run on the node, each in a container with a socket and grants of its own. keg system ls, install, start, stop and rm look after them.

No. 04From outside

Services From Outside, Behind Walls

A folder with a keg.service.toml is installed with keg system install. You are asked about each thing it asks for, in plain words, and it holds only what you allowed: pinned by digest, no network but its socket, memory, processes and disk capped. Building one from its folder on the node is off until you turn it on with keg system builds on; off, a service names its image by digest. What a service may rely on.

07

Your tools, as they are.

Use Keg's own command, or point docker at Keg and change nothing else. Either way the containers, images and volumes are the same ones, and show in the app.

The keg commandListing 01
# Run a web server; it opens by name $ keg run --name web -p 8080:80 nginx:1.27 http://web.keg.localhost # Follow its output $ keg logs -f web "GET / HTTP/1.1" 200 # A shell in it, or in a new container $ keg exec -it web sh $ keg run -it --rm alpine:3.20
Docker, through KegListing 02
# Point docker at Keg, once $ keg docker use $ docker run --rm -p 8080:80 nginx $ docker build -t myapp:dev . $ docker exec -it web sh # Bring what you had with you $ keg migrate --from desktop-linux
08

Your Compose files. As written.

Health checks, depends_on, service names, volumes and builds. Run them with Keg's command or with docker compose.

compose.yamlListing 03

09

From laptop to server, with a person in the loop.

Install Keg on a Linux server you run, and it becomes a node your Mac can deploy to. What moves is the image you tested, never a rebuild.

01

Describe and deploy

keg init writes a keg.yaml and a Dockerfile for the project it finds, or keg example makes one to try. keg up builds, releases and runs it locally.

keg example hello-keg keg up https://hello-keg.keg.localhost
02

Propose

Make an environment that waits for a person, and propose the release to it. To a server you run, keg promote sends the exact image, only the layers it lacks, over mutual TLS.

keg env add staging --policy manual keg up --env staging waiting for a person
03

Approve, or roll back

See what would change and the checks it passed, then approve in the app or the terminal. The release before is one command away.

keg approve 3 --env staging keg rollback hello-keg \ --env staging
