# Managed Agents Research — Cursor (Cloud Agents / Background Agents)

## Scope

Covered: Cursor's cloud-agent product line as of 2026-09-29 — the renamed **Cloud Agents** (formerly Background Agents), their execution substrate (Cursor-hosted Firecracker microVMs, self-hosted machines, third-party sandbox providers), the Builds/environment model, session lifecycle (hibernate/resume), human-in-the-loop surfaces, and pricing posture. Sources are exclusively Cursor's own docs (cursor.com/docs), changelog (cursor.com/changelog), pricing pages, and an official Cursor-staff forum answer.

Deliberately skipped: desktop IDE agent features (worktrees, sandboxed terminals, Bugbot/Rollouts bots — noted only where they touch cloud agents), Cursor Projects (beta coordinator layer — mentioned briefly as it runs on Cloud Agents), and third-party comparisons.

## Key Findings

1. **The product was renamed: "Background Agents" → "Cloud Agents" in Cursor 2.0 (Oct 29, 2025).** The docs carry an explicit "Naming History" note; searching old material under "background agents" still works. ([changelog/2-0](https://cursor.com/changelog/2-0), [docs/cloud-agent](https://cursor.com/docs/cloud-agent))

2. **Execution substrate: one Firecracker microVM per agent in a dedicated AWS account, running Ubuntu with a full desktop environment.** "Each agent runs in its own VM boundary, not a shared process sandbox"; "Runtime workspaces run on Firecracker-based microVM infrastructure"; VMs run in an AWS account separate from the rest of Cursor's production. Each VM gets a cloned repo, installed dependencies, injected secrets, and network access. Specs are not published: docs say only "a default VM profile with limited memory and CPU," with larger limits available to Enterprise workspaces on request and self-serve sizing "coming soon." ([security](https://cursor.com/docs/cloud-agent/security), [setup](https://cursor.com/docs/cloud-agent/setup))

3. **The continuation primitive is a git branch + draft PR, not live process migration.** A run's lifecycle is: Start → Provision → Run → Persist (conversation state saved to Cursor storage) → **Hand off (push branch, open a draft PR for human review)** → Recycle (VM hibernates, then deleted on idle timers). "Nothing merges until a person reviews the change." So the durable checkpoint is (repo branch, persisted conversation/artifact state), and the VM itself is disposable. VM disk snapshots persist 90 days of inactivity to speed re-starts; conversation state is kept indefinitely by default. ([security](https://cursor.com/docs/cloud-agent/security))

4. **Sessions are resumable across surfaces via persisted conversation state + hibernating VMs.** The agent loop can be started from Cursor desktop (select "Cloud" in the agent-input dropdown), Cursor Web (cursor.com/agents), Cursor iOS, Slack (`@cursor`), GitHub/Bitbucket PR or issue comments (`@cursor`), Linear, and an API. Follow-up messages wake a hibernated run ("The timer refreshes when you send follow-up prompts"); teammates can send "team follow-ups" to another user's agent if an admin enables it. Cursor 2.0 explicitly "improved the experience of sending agents to the cloud from the editor." I found **no** docs describing migrating a *local in-progress IDE agent session* into a cloud VM with its local state intact — surfaces share runs and follow-ups, but the local working tree is handed off via git, not via live state transfer (inference from the git-centric handoff docs). ([cloud-agent](https://cursor.com/docs/cloud-agent), [settings](https://cursor.com/docs/cloud-agent/settings), [changelog/2-0](https://cursor.com/changelog/2-0))

5. **Environments are the real product: Builds are bootable snapshots prepared ahead of agent runs.** A Build clones repos at a recorded commit SHA, runs an `install` script, snapshots the disk, and becomes the warm start for all agents in that environment. Triggers: recurring (skipped when nothing changed), config/secret change, manual, agent-requested. A failed Build never replaces the active one. Environment config lives in `.cursor/environment.json` (Dockerfile, install/start/terminals commands), a personal saved environment, or a team environment, resolved in that order. **Builds are included at no extra charge.** Builds preserve disk only — processes/ENV don't survive; `start` and `terminals` (shared tmux with the human) re-run per agent start. ([builds](https://cursor.com/docs/cloud-agent/builds), [setup](https://cursor.com/docs/cloud-agent/setup))

6. **Human-in-the-loop is layered: draft-PR review, remote desktop takeover, and shared tmux terminals.** A human can take control of the agent's remote desktop, test the software, and "release control back to the agent"; `terminals` run app processes in a tmux session shared between human and agent; artifacts (screenshots, videos, logs) attach to the PR. Agents auto-run terminal commands (more autonomous than the foreground agent) and auto-fix CI failures on their own PRs (GitHub Actions only, capped at 10 follow-ups). Event "subscriptions" (GitHub PR/CI, Slack, Linear, timers, ≤180 days) let an agent end its turn and wake on external events. ([capabilities](https://cursor.com/docs/cloud-agent/capabilities), [security](https://cursor.com/docs/cloud-agent/security))

7. **The control plane is unmistakably cloud-side: the agent loop runs in Cursor's backend even when execution is on your machine.** Self-Hosted Machines ("My Machines" for individuals, "Team Pools" for fleets) run a local `agent worker` CLI (installed via `curl https://cursor.com/install`) that opens an outbound-only connection; "The agent loop runs in Cursor's cloud, but terminal commands, file edits, browser actions, and other tool calls execute on your machine." Team Pools can hibernate idle machines and restore them within a reconnect window. Computer-use on a self-hosted Mac requires a "Cursor Computer Use" helper app with Accessibility + Screen Recording permissions. Separately, cloud agents can execute on third-party sandbox providers: AWS Lambda, Coder, Cloudflare, Daytona, Modal, Namespace, Vercel, and E2B. ([my-machines](https://cursor.com/docs/cloud-agent/self-hosted-guides/my-machines), [changelog](https://cursor.com/changelog))

8. **What it manages: repo/git via a GitHub/GitLab/Azure DevOps/Bitbucket app install (org-level grant + per-user account link; "access is inherited, never widened"), secrets via a dashboard Secrets tab** (KMS-encrypted, injected as env vars at agent start, environment-scoped variants, "Runtime Secrets" redacted from transcripts/commits, OIDC tokens minted from a local socket for AWS/GCP/Azure federation), **network via three egress modes** (allow-all / default+allowlist / allowlist-only, lockable org-wide), **checkpoints via Builds + VM snapshots + persisted transcripts** (per-agent AES-256 keys, CMEK/BYOK on Enterprise). ([security](https://cursor.com/docs/cloud-agent/security), [setup](https://cursor.com/docs/cloud-agent/setup))

9. **Pricing posture: cloud agents are included in paid plans and metered only on model tokens — no VM/compute surcharge.** Cloud Agents require a paid plan (Hobby excluded); Pro $20/mo, Pro+ $60/mo, Ultra $200/mo list "Cloud agents" as included; Teams $40/user/mo (Standard) / $120 (Premium). Billing: "Cloud Agents are charged at API pricing for the selected model," drawing from the plan's included usage pools first, then on-demand at the same rates, with a mandatory spend limit on first use. A Cursor staff answer on the official forum states: "There's no separate VM, compute, or memory charge for Cloud Agents." On Teams/Enterprise, third-party model usage adds a "Cursor Token Rate" of $0.25/M tokens (first-party Grok/Composer exempt). Builds are free. VM size increases are an Enterprise support conversation, not a SKU. ([pricing](https://cursor.com/pricing), [account/pricing](https://cursor.com/docs/account/pricing), [cloud-agent billing](https://cursor.com/docs/cloud-agent), [forum staff answer](https://forum.cursor.com/t/what-is-the-pricing-structure-for-using-cloud-agents/156843/14))

10. **Everything is attributable and auditable: HSM-signed Ed25519 agent commits** (GitHub "Verified" badge, satisfies signed-commit branch protection), per-agent encryption keys, admin dashboard review, audit-log streaming to SIEM (Enterprise), and a built-in "Cursor Cloud MCP" giving the agent (and admins) introspection into run transcripts, events, builds, and egress policy. ([security](https://cursor.com/docs/cloud-agent/security), [capabilities](https://cursor.com/docs/cloud-agent/capabilities))

## Comparison notes

- **Substrate:** one Firecracker microVM per agent, Ubuntu + full desktop, in a dedicated AWS account; Docker available inside (fuse-overlayfs/iptables-legacy quirks documented). Third-party sandbox providers (E2B, Daytona, Modal, Vercel, etc.) and self-hosted machines (outbound-only worker CLI; macOS workers supported with a computer-use helper app) are alternative execution targets.
- **Control plane:** Cursor's cloud owns the agent loop in all modes (even self-hosted machines); provisioning, snapshots, capacity, artifacts, and transcripts are Cursor-managed. The local component is the editor/CLI/web/iOS/Slack surface plus, optionally, the `agent worker`.
- **Continuation model:** no live migration. Durable state = git branch/draft PR + persisted conversation + Build/snapshot layers; VMs hibernate and are recycled on idle timers; resume = send a follow-up from any surface. Cross-machine handoff is via the repo, not process state.
- **Checkpoints:** Builds (bootable env snapshots, provenance with commit SHAs), VM disk snapshots (90-day inactivity expiry), indefinite conversation retention (deletable; Enterprise retention policies). Cursor desktop's local "checkpoints" feature is separate and not the cloud-agent resume mechanism.
- **Human-in-the-loop:** draft PR before merge (hard gate), remote desktop takeover, shared tmux terminals, team follow-ups (admin-gated), auto-CI-fix with caps, event subscriptions for long waits.
- **Pricing:** included in Pro+; metered at the chosen model's API rate against usage pools; no separate compute/VM/memory charge; Builds free; spend limits mandatory; Teams adds $0.25/M-token Cursor Token Rate on third-party models.
- **Local component:** the IDE is a launch/monitor surface, not the executor; "Start from scratch" mode now even removes the repo requirement (Cursor hosts an Origin repo for you).

## Unverified / uncertain

- **Exact VM specs** (vCPU/RAM/disk of the "default VM profile") are not published anywhere I could find in primary sources; only "limited memory and CPU" plus an Enterprise support path to raise limits.
- **Whether a local desktop agent turn can be promoted to a cloud run carrying its in-editor state** — docs describe "sending agents to the cloud from the editor" and shared runs/follow-ups, but I found no primary-source description of stateful local→cloud session transfer; the evidence points to git-based handoff (inference).
- **Cloud-agent concurrency limits** (beyond the 2.0-era "up to eight agents in parallel" for multi-agent in the editor) and any per-plan cloud-agent caps beyond token billing.
- **Self-hosted machines availability tier**: docs don't clearly state which plans can use My Machines/Team Pools.
- Cursor **Projects** (beta, launched ~2026-09-23) is a coordinator layer over Cloud Agents with a shared-context file set that syncs "across every cloud and local machine" — noted, but its mechanics and pricing are not yet documented in primary sources I fetched. ([changelog](https://cursor.com/changelog))
